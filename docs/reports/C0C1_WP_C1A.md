## 3. Spot taxonomy

### 3.1 Preflop

Key shape depends on the family so that the brief's own examples come out verbatim.

| Family | Condition at the decision | Key | Rationale |
| --- | --- | --- | --- |
| `RFI` | 0 raises, 0 limps in front; position ≠ BB | `BTN_RFI` | The open decision. First-in is structurally different from entering behind money. |
| `VS_LIMP` | 0 raises, ≥1 limp in front | `CO_VS_LIMP` | Isolation is not an open; conflating them corrupts both. |
| `BB_OPTION` | 0 raises; position = BB | `BB_OPTION` | The BB is already in for a full blind and acts last; its check is not a fold and not a VPIP. |
| `VS_OPEN` | exactly 1 raise, 0 cold-callers | `BB_VS_BTN_OPEN` | The core defence spot, split by opener position. |
| `SQUEEZE` | exactly 1 raise, ≥1 cold-caller | `BB_SQUEEZE_VS_CO` | Multiway defence prices differently from heads-up defence. |
| `VS_THREE_BET` | 2 raises AND this seat made raise #1 | `HJ_OPEN_FACING_BTN_3BET` | Only the opener is "facing a 3-bet"; a cold-caller in the same spot is a different problem. |
| `VS_FOUR_BET` | 3 raises AND this seat made raise #2 | `BTN_3BET_FACING_HJ_4BET` | Same reasoning one level up. |
| `VS_MULTI_RAISE` | anything else (≥2 raises without the above role, ≥4 raises) | `SB_VS_MULTI_RAISE` | Honest catch-all. Real but rare lines are recorded, not discarded (prompt §31), and not given per-line buckets we would never fill. |

Dimensions: `family` (8) × `position` (6) × `opponentPosition` (6 or n/a) — bounded at a
few hundred keys, most of which never occur. `lineup` is carried on the descriptor but is
deliberately NOT in the preflop key: preflop spot identity is already carried by the family
plus the two positions, and adding it would double the bucket count for no new question.

### 3.2 Postflop

Key: `{street}_{family}_{position}_{relation}_{lineup}_{potType}[_{facingSize}]`
e.g. `TURN_FACING_CBET_BB_OOP_HEADS_UP_THREE_BET_MEDIUM`.

| Dimension | Buckets | Rationale |
| --- | --- | --- |
| `street` | `FLOP` `TURN` `RIVER` | Streets are not interchangeable. |
| `family` | `CBET` (has initiative, no bet yet) · `FACING_CBET` (facing the initiative holder's first bet) · `DONK_LEAD` (no initiative, first to act, no bet yet) · `CHECKED_TO` (no initiative, no bet yet, not first) · `FACING_BET` (a first bet by someone without initiative) · `FACING_RAISE` (2nd+ aggression this street) | Every member names an OPPORTUNITY, never an action. There is deliberately no `CHECK_RAISE` family — see §5. |
| `position` | 6 | The seat's own position, so a spot can be read positionally. |
| `relation` | `IP` `OOP` | Taken from `poker-core`'s `postflopOrder` over the LIVE seats, not from a position-name heuristic. Multiway is reduced to the same binary: last to act = IP. |
| `lineup` | `HEADS_UP` `MULTIWAY` | Contender count at the decision. Three-way and four-way share a bucket on purpose — the sample would never support splitting them. |
| `potType` | `LIMPED` `SINGLE_RAISED` `THREE_BET` `FOUR_BET_PLUS` | From the total preflop raise count. SPR and range shape differ sharply per bucket. |
| `facingSize` | `NONE` `TINY`≤33% `SMALL`≤50% `MEDIUM`≤75% `LARGE`≤90% `POT`≤110% `OVERBET`>110% | Fraction of the pot BEFORE the bet, compared by cross-multiplication of integers (no float). `NONE` when not facing a bet — a distinct bucket, not a zero-sized bet. Segment omitted from the key when `NONE`. |

Theoretical ceiling 3 × 6 × 6 × 2 × 2 × 4 × 7; the reachable set is far smaller (`CBET`
cannot be `MULTIWAY`+`FACING_*`, etc.). Bounded and constant in the number of hands, which
is the requirement (prompt §18).

### 3.3 Bet-size buckets (PRODUCT HEURISTIC, `modelConfig.ts`)

Preflop raise-TO, in hundredths of a BB, inclusive upper bounds:
`LIMP` ≤1 BB · `MIN` ≤2.20 · `SMALL` ≤2.60 · `STANDARD` ≤3.20 · `LARGE` ≤4.50 · `HUGE` >4.50.

The raw integer milliBB `toAmount`, `amount`, `potBefore`, `currentBetBefore` and
`bigBlind` are all preserved on every `BetSizeObservation`; the bucket is an extra label
and the fractions are derived on demand.

## 4. Opportunity-detection rules — exact denominator per stat

An opportunity exists **iff** `poker-core` produced an `ActionRecord` for that seat at that
point, i.e. the engine actually put the seat on the clock. Nothing is inferred from a
position. `HandState.actions` is the single source; the walk in `decisions.ts` only adds
context labels.

| Stat | Denominator (opportunity) | Numerator (action) |
| --- | --- | --- |
| `VPIP` | the player faced ≥1 preflop decision | any preflop effect ∈ {CALL, BET, RAISE} |
| `PFR` | the player faced ≥1 preflop decision | any preflop effect ∈ {RAISE, BET} |
| `RFI` | first preflop decision with 0 raises and 0 limps in front (family `RFI`) | that decision's effect is RAISE |
| `STEAL_ATTEMPT` | the `RFI` opportunity, AND own position ∈ {CO, BTN, SB} | that decision's effect is RAISE |
| `FOLD_TO_STEAL` | first `VS_OPEN` decision where own position ∈ {SB, BB} and opener ∈ {CO, BTN, SB} | effect is FOLD |
| `THREE_BET` | first preflop decision with exactly 1 raise in front (covers `VS_OPEN` and `SQUEEZE`) | effect is RAISE |
| `FOLD_TO_THREE_BET` | first `VS_THREE_BET` decision — this seat made raise #1 and now faces raise #2 | effect is FOLD |
| `FOUR_BET` | the same decision as `FOLD_TO_THREE_BET` | effect is RAISE |
| `CBET_{FLOP,TURN,RIVER}` | first decision on that street with initiative (previous street's last aggressor) and no bet yet in front | effect is BET |
| `FOLD_TO_CBET_{…}` | first decision on that street facing the street's ONLY aggression so far, made by the initiative holder | effect is FOLD |
| `CHECK_RAISE_{…}` | first decision on that street where the seat's last action this street was a CHECK and it now faces a bet | effect is RAISE |
| `TURN_BARREL` | c-bet the flop (opportunity existed AND taken) **and** a `CBET_TURN` opportunity exists | the turn c-bet was taken |
| `RIVER_BARREL` | c-bet the turn **and** a `CBET_RIVER` opportunity exists | the river c-bet was taken |
| `WTSD` | the board reached ≥3 cards and the player did not fold preflop | the hand ended `SHOWDOWN` and the player's final status is `IN_HAND`/`ALL_IN` |
| `WSD` | reached the showdown (the `WTSD` numerator) | `seats[seat].wonGross > 0` |

Every stat is recorded **twice** per opportunity: once in the `position: null` bucket and
once in the player's positional bucket. Per ADR-0035 these are separate buckets and are
never summed — the aggregate row is not the sum of six positional rows.

Notes that follow from these rules and are asserted by tests:

- Folded → no later `ActionRecord` → no later opportunity, on any street.
- All-in → `seatsAbleToAct` skips it → no later betting opportunity (it can still reach a
  showdown, so `WTSD`/`WSD` still apply — those are about the hand, not about acting).
- Sitting out → not in `dealtInSeats` → nothing at all, and the lineup stays the real one.
- Folded round to a walk → the BB never acts → **zero** stats, not a VPIP denominator.
- A limped pot has no initiative holder, so nobody gets a `CBET_*` or `FOLD_TO_CBET_*`
  opportunity on it. This is deliberate: a bet in a limped pot continues nothing.
- A short all-in that cannot cover the call is effect `CALL`; the verb stays `ALL_IN`.

## 5. What I deliberately did NOT count

1. **No `CHECK_RAISE` spot family.** "Already checked and facing a bet" is a question about
   the same situation `FACING_CBET`/`FACING_BET` already names. Giving it a family would
   double the postflop buckets and would mislabel the far commoner check-**fold**. The
   check-raise question is counted exactly, as its own global stat, off
   `Decision.hasCheckedThisStreet`.
2. **No board-texture dimension.** Prompt §18 lists it as *may include*. It needs a texture
   classifier that does not exist in this repo, and inventing one would be a poker claim
   (CLAUDE.md rule 7). The board is preserved on `ShowEvidence`; the dimension can be added
   later behind an `ANALYSIS_ALGORITHM_VERSION` bump with no change to raw history.
3. **No stack-depth bucket in the spot key.** `strategy-core` has a `stackBucket` module,
   but importing it is forbidden (ADR-0061) and duplicating its boundaries here would
   create a second, silently-drifting definition. `effectiveStackBefore` is on the
   `ActionRecord` inside every `Decision`, so nothing is lost.
4. **No 3-way/4-way split.** `MULTIWAY` is one bucket.
5. **No limp sizing observation.** `BetSizeObservation` records aggressive actions only;
   a limp has no size question.
6. **No derived adjectives.** No TIGHT/LOOSE/AGGRESSIVE anywhere. Prompt §21 permits them
   as explicitly-heuristic presentation labels; that is a UI decision, not an engine one.
7. **No rate stored anywhere.** Counts only, everywhere (ADR-0035).
8. **`ObservedMetric` was not widened.** The four existing members and their DB CHECK are
   untouched; `ModelStatKey` is a separate vocabulary for a separate record type
   (ADR-0062a), so this WP implies no migration.
9. **No `NO_CHANGES` decision here.** `computePlayerModel` produces `inputHash` +
   `analysisAlgorithmVersion`; comparing them against the player's latest snapshot is the
   persistence layer's job.

## 6. Determinism

- No clock, no RNG, no id generation anywhere in the package. `createdAt` and
  `modelVersion` are absent from `PlayerModelContent` on purpose — the persistence layer
  supplies them (ADR-0040).
- `globalStats` sorted by `MODEL_STAT_KEYS` order then position (`null` first, then
  `OBSERVED_POSITIONS` order). `spotStats` sorted by `spotKey`. `showEvidence` sorted by
  `handId`. `betSizes` **stably** sorted by `handId`, so within-hand decision order is
  preserved and across-hand input order stops mattering.
- Rows with zero opportunities are never emitted.
- `confidenceWeightBps` is computed in pure integer arithmetic
  (`floor((2·num + den) / (2·den))` = round-half-up), so it is bit-identical on every
  machine — important because snapshots are compared for equality.
- Asserted: same hands → `JSON.stringify`-identical; hands reversed or shuffled →
  identical.

### `inputIdentityHash`

FNV-1a 64-bit over `count + '\n' + sortedIds.join('\n')`, rendered as 16 lowercase hex
digits. Order-independent (sorts first), dependency-free, no `crypto`.

**Collision trade-off, stated:** FNV-1a is non-cryptographic and trivially collidable by an
attacker who chooses the inputs. Accepted, because the inputs are locally-generated hand ids
from the user's own database with no adversary, and the only consequence of a collision is a
run reporting `NO_CHANGES` when a new hand had arrived. Accidental collision probability at
64 bits across a million distinct input sets is ≈3 × 10⁻⁸. If hand ids ever become
attacker-chosen, swap to SHA-256 and bump `ANALYSIS_ALGORITHM_VERSION`.

## 7. Confidence (ADR-0062e)

`confidenceWeightBps(n, K=30) = round(10000 · n / (n + K))`, integer BPS. Display states
`UNKNOWN` (n<5) / `LEARNING` (5≤n<30) / `KNOWN` (n≥30). K and both thresholds live in one
object, `DEFAULT_SNAPSHOT_CONFIDENCE_CONFIG`, documented as a PRODUCT HEURISTIC.

Hand-verified values, all covered by tests: n=0→0, 1→323, 5→1429, 22→4231, 30→5000 (exactly
half, by construction), 90→7500, 270→9000, 2970→9900, 100 000→9997. The exact ratio never
reaches 1, but the *rounded* BPS reaches 10 000 around n≈600 000 — documented rather than
clamped.

This is a **new concept alongside** `confidence.ts`'s `ConfidenceLevel`, which is untouched
and unchanged (ADR-0036 stands). The two are separate types and there is no implicit
conversion between them. Confidence is attached **per situation** (`ModelStatCount`,
`SpotStatCount`) and once at snapshot level over the hand count — 1000 hands says nothing
about a spot that arose 7 times.

## 10. Open questions for the downstream WPs

### For C1-C (snapshot persistence)

1. **`PlayerModelContent` → rows.** `globalStats` and `spotStats` are flat count rows and
   map naturally onto `player_model_snapshots` / `player_spot_stats` in ADR-0062a.
   `showEvidence` and `betSizes` have **no table named in ADR-0062a**. Decide: extra tables,
   or a JSON document column on the snapshot (ADR-0038 precedent)? My recommendation:
   separate insert-only tables — `betSizes` grows linearly with hands and a JSON blob would
   make it unqueryable, which defeats the point of storing raw amounts.
2. **`confidence` is stored on every row.** It is fully derivable from `opportunities` + the
   config. Storing it is optional; storing the *config* (`k`, both thresholds — already on
   `SnapshotConfidenceMetadata`) is not, or an old snapshot becomes uninterpretable.
3. **`inputHash` is over the ids the caller passed.** For `NO_CHANGES` to be correct, the
   caller must pass exactly the player's eligible linked set — `hand_players.player_id` on
   hands with `finished_at` set — in every run, no more and no less. If the query ever
   changes shape, the hash changes and a spurious snapshot is written.
4. **`ShowEvidence.cards` may hold ONE card.** `HOLE_CARDS_SET` accepts a partial reveal;
   the length is not fixed at 2. A `CHECK(length = 2)` would reject legal data.
5. **All money fields on `BetSizeObservation`/`ShowEvidence` are plain `number` milliBB**
   (`player-core` cannot depend on `poker-core`'s money helpers beyond `shared`). They still
   need the `isIntegral` + `moneyRange` CHECKs (ADR-0041).

### For C1-B (server orchestration)

6. **Errors are `AnalysisResult`, not throws** — except two `invariant`-style throws in
   `actionEffect`/`actionVerb` for an `ActionRecord` carrying a non-action kind, which would
   be a `poker-core` change, not user data. Worth catching at the run boundary so one bad
   hand degrades to `PARTIAL`, not a 500.
7. **`playersInHands(hands)` gives the scope discovery** ADR-0062b describes, without
   re-implementing extraction.
8. **Cost.** `computePlayerModel` re-extracts every hand per player, so an N-player,
   M-hand run is O(N·M) extractions. Fine at session scale; if it bites, extract once per
   hand and fan out — the extraction result is already per-player.

### For C1-D (UI)

9. **The `position: null` row and the six positional rows must never be added together.**
   They are separate buckets over the same decisions (ADR-0035). A "total" that sums them
   is a bug.
10. **Rates are derived, never stored.** `modelStatRate` / `spotEffectRate` /
    `betFractionOfPot` / `toAmountInBigBlinds` all return `null` for an empty denominator so
    the UI can distinguish "no data" from 0%.
11. **`UNKNOWN` must render as a distinct state, not as "14%".** That is the whole point of
    the three-state display (ADR-0036's posture, carried into ADR-0062e).
12. **Verb vs effect.** `SpotStatCount` carries both. A player who shoved is counted as
    having raised (effect) but the `ALL_IN` verb is still visible — show it.

### Not addressed by this WP

13. A `null`-`playerId` dealt-in seat is handled (skipped for attribution, kept as lineup
    context) but is **not reachable** through today's table API: `seatPlayer` requires an
    identity and `dealtInSeats` filters on `playerId !== null`. The path exists for a future
    hand-history importer and is therefore untested. Flagged rather than deleted.
14. `sourceObservationCount` is defined as the number of DECISIONS observed (= total spot
    observations), not the number of stat opportunities, which would double-count the
    positional buckets. If the UI wants "observations" to mean something else, say so.

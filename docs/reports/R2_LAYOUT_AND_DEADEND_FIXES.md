## 2. 최종 레이아웃 규칙과 숫자 근거

### 2.1 트레이 높이

```
평상시(팔레트/힌트): min-h = max-h = min(18.5rem, calc(100vh - 26.5rem))
어워드 패널:          min-h = min(18.5rem, calc(100vh - 26.5rem)), max-h = 26rem
```

- **`26.5rem`(424px)** — 펠트가 자기 콘텐츠 높이를 온전히 갖고 남는 것이 트레이 몫이다.
  측정값: 헤더 위쪽 **59px** + 액션 독 **61px** + 펠트 **304px**(좌석 그리드 자연 높이 + 펠트 `p-2`;
  핸드 진행 중 288px, 핸드 사이 304px, 1024~1440 폭에서 동일 — 그리드 높이는 좌석 카드 콘텐츠지
  레이아웃이 아니다). 59+61+304 = **424**.
- **`18.5rem`(296px)** — 트레이가 원하는 값. 56×64 팔레트 = 274px 그리드 + 4px 자체 패딩 + 12px `py-1.5`.
  뷰포트 720px 이상에서 실제로 이 값을 받는다.
- **floor == cap (평상시)** — 팔레트 열림/닫힘에서 트레이 높이가 **정확히 같다**. ADR-0054의
  "no-jump" 절반을 그대로 유지하며, `action-dock.spec.ts`의 `trayAfter.y === trayBefore` assertion이
  이것을 고정한다.
- **어워드만 예외** — ADR-0054가 명시한, 펠트가 흡수하는 유일한 경우. 돈을 움직이는 패널의 제출
  버튼이 독 밑에 깔리면 안 되므로 cap을 26rem으로 연다. (1280×560 어워드 실측: 트레이 169px,
  제출 버튼 bottom 493 < 독 top 499 — 통과.)

### 2.2 카드 크기 전환점

```
기본:                                        h-13 w-11 (52×44px) — WP-8 하한
@media (min-width:1152px) and (min-height:680px): h-16 w-14 (64×56px) — WP-8 데스크톱 밴드
```

- **1152px(폭)** — 56px 행은 `13*56 + 12*6 + 8 = 808px`. 트레이는 그리드에 `뷰포트 − 309px`를
  준다(히어로 카드 열 + 224px 프롬프트 열 + gap). 808px는 **1117px** 뷰포트를 요구한다.
  기존 전환점은 `sm:`(640px)이었고, 그래서 640~1116px 구간에서 행이 컨테이너를 조용히 넘쳤다
  (1024×640에서 `palette-2s`가 x 1049–1105). 실제 화면 크기로 올림해 **1152**.
- **680px(높이)** — 64px 행은 274px 그리드가 필요하고, 트레이가 줄 수 있는 건 `100vh − 424`이므로
  **674px** 뷰포트가 필요하다. 올림해 **680**.
- 그 아래는 44×52 — WP-8 하한 준수. `13*44 + 12*4 + 8 = 628px`로, 1024px 뷰포트에서 트레이가
  주는 704px 안에 들어간다(실측 `scrollWidth == clientWidth`).

### 2.3 스크롤 안전망 (보이는 스크롤)

- **세로(트레이 안쪽)**: `overflow-y-auto` + `scrollbar-width:thin` + `scrollbar-color` +
  **`scrollbar-gutter:stable`**. `scrollbar-color`만으로는 Chromium이 오버레이 스크롤바를 유지했다
  (실측: 실제로 스크롤 중인데 `offsetWidth == clientWidth`). gutter를 켠 뒤 **11px** 실측 →
  레이아웃에 자리를 차지하는 진짜 스크롤바. 세로 gutter는 **폭**만 먹으므로 높이 예산에 영향 없음.
- **가로(팔레트 그리드)**: 같은 스타일 + `scrollbar-gutter:stable`을 **1024px 미만에서만** 적용.
  가로 gutter는 블록 끝(=높이)을 먹기 때문에, 넘치지 않는 폭에서 상시 예약하면 팔레트 높이 예산을
  깎는다. 1024px 이상에서는 실측상 **아예 넘치지 않는다**(모든 뷰포트에서 `scrollWidth == clientWidth`).

### 도달 가능성 판정 방법

Playwright `.click()`은 `scrollIntoViewIfNeeded`를 부르므로 판정에 쓰지 않았다. 대신
카드 중심점에 `document.elementFromPoint`를 쏘아 **그 버튼 자신이 나오는지**로 판정했고,
안 나오는 카드는 스크롤 컨테이너를 스크롤해 다시 판정했다. 스크롤이 필요한 경우
스크롤바가 **레이아웃에 자리를 차지하는지**(`offsetWidth − clientWidth = 11px`)까지 측정했다.

### 알려진 한계 (물리적으로 불가능한 조합)

600px 이하 높이에서 **팔레트 52장 동시 표시 + 좌석 미가림**은 동시에 만족할 수 없다:
44×52 하한 그리드 220px + 펠트 304px + 헤더·독 120px = **644px** 요구. 600px 화면에는 없다.
이때 양보하는 쪽은 **팔레트**(보이는 스크롤바와 함께 트레이 안에서 스크롤)이고, 좌석과 독은
절대 양보하지 않는다. 이는 296px floor 이전(152px floor 시절)과 같은 성질의 거동이다.

## 4. 3번 항목 — 사용자에게 보여줄 최종 문구

`copy.ts` `settlementBlockedGuidance(code, zeroStackSeats)`. 엔진 오류 배너 아래에
`data-testid="settlement-blocked-guidance"`로 렌더된다. 엔진 코드·메시지·스토어는 무수정.

**`NOT_ENOUGH_PLAYERS` + COMPLETE 핸드 대기:**

> 끝난 핸드를 정산하려면 다음 핸드를 딜할 좌석이 2개 이상 필요한데, 칩이 남는 좌석이 모자랍니다.
> 이 상태에서는 스택 수정과 플레이어 교체가 모두 거부되므로 다음 중 하나를 먼저 하세요:
> 칩이 0인 좌석의 [자동 리바이]를 켜거나, 빈 좌석에 [플레이어 변경]으로 플레이어를 앉히세요.
> 그다음 [핸드 시작]을 누르면 정산되고 다음 핸드가 딜됩니다. 지금 칩이 0인 좌석: 좌석 2.

**`HAND_ALREADY_FINISHED` + COMPLETE 핸드 대기:**

> 끝난 핸드가 아직 정산되지 않아 거부되었습니다. [핸드 시작]을 누르면 정산됩니다.
> [핸드 시작]까지 인원 부족으로 거부되면, 칩이 0인 좌석의 [자동 리바이]를 켜거나
> 빈 좌석에 [플레이어 변경]으로 플레이어를 앉힌 뒤 다시 [핸드 시작]을 누르세요. 지금 칩이 0인 좌석: 좌석 2.

**플레이어 교체 사전 거부 (5번 항목과 같은 지점):**

> 끝난 핸드가 아직 정산되지 않아 이 좌석의 플레이어를 바꿀 수 없습니다. [핸드 시작]을 누르면 정산됩니다.
> [핸드 시작]이 인원 부족으로 거부되면, 칩이 0이 된 좌석의 [자동 리바이]를 켜거나
> 빈 좌석에 플레이어를 앉힌 뒤 다시 [핸드 시작]을 누르세요.

`지금 칩이 0인 좌석: …`은 **끝난 핸드의 view를 그대로 읽은 값**이고(정산 결과를 예측한 것이 아님),
읽을 값이 없으면 문장 자체가 생략된다. 지어내지 않는다.

**브라우저 실증** (헤즈업 200BB vs 3BB, 둘 다 올인, 보드 딜, 좌석 1 팟 획득 → COMPLETE):

```
after 핸드 시작        → NOT_ENOUGH_PLAYERS + 안내 (칩이 0인 좌석: 좌석 2)
after 스택 수정        → HAND_ALREADY_FINISHED + 안내
after 좌석2 자동리바이 → 핸드 시작 성공, 핸드 #1 딜됨, phase=액션 대기
```

즉 안내가 지목한 출구가 **실제로 통한다**.

## 5. 4번 / 5번 항목

**4. `hand-number` testid** — `helpers.ts`의 `handCounter`가 `page.getByTestId('hand-number')`를
쓴다. `HAND_COUNTER` 한국어 정규식은 삭제. `handNumber()`는 `/^\d+$/`로 검증하고
(`Number('')`가 0이 되어 조용히 0을 반환하는 함정을 막는다) 숫자를 반환한다. 주석은
"testid가 없다"에서 "WP-4가 testid를 붙였으므로 예외가 사라졌다"로 사실화. E2E 32/32 유지 확인.

**5. 서버 쓰기 순서** — `handleSwapSubmit`이 `replaceSeatPlayer`(서버) **이전에** 스토어가 거부할
조건을 읽고 거부한다: 좌석이 비어 있지 않고, 실제 변경이며(같은 플레이어 재지정은 no-op이라 통과),
COMPLETE 핸드가 대기 중이고, 그 핸드가 **그 좌석을 딜인**했을 때. 스토어의 자체 가드와 동일한
좁은 조건을 **읽기만** 한다(스토어 API 무수정). 거부되면 서버 호출 자체가 없으므로 DB/메모리가
갈라지는 경로가 사라진다. `seatPlayerStoreRefusedNotice`는 예측 못한 divergence용 fallback으로 남는다.

테스트: 기존 R1 테스트를 **더 강한** 계약으로 갱신(`replaceSeatPlayer` 미호출 + `syncSessionSeats`
미호출 + 패널 유지 + 좌석 불변), 그리고 **음성 대조군** 추가 — 끝난 핸드가 딜인하지 않은 좌석은
여전히 서버로 간다(가드가 스토어보다 엄격해지지 않았음을 고정).

## 7. 남은 위험

1. **기존 플래키 벤치마크** — `packages/strategy-core/src/postflop/benchmark.test.ts`의
   "names the worst shape by MEASUREMENT" 가 전체 실행 7회 중 1회 실패했다
   (`expected 176.275 to be greater than 176.837` — 두 지연 측정값의 대소 비교).
   내 변경과 무관한 **기존 성능 측정 테스트의 시간 의존 플래키**다. 6/7회 통과.
2. **560~600px 높이에서 팔레트 세로 스크롤** — §3의 "알려진 한계". 좌석·독은 항상 온전하지만
   52장이 한눈에 들어오지 않는다. 해소하려면 좌석 카드 아래 컨트롤(자동 리바이/자리비움/버튼 행)의
   높이를 줄여 펠트 요구(304px)를 낮추는 별도 작업이 필요하다 — 이번 범위 밖.
3. **`scrollbar-gutter` 브라우저 의존** — Chromium에서 11px 실측으로 확인했다. Firefox/Safari는
   측정하지 않았다(이 앱의 E2E 대상은 Chromium).
4. **`settlementBlockedGuidance`의 트리거 조건** — 오류 코드 + COMPLETE 핸드 대기라는 **관측**으로
   상태를 인식한다. 즉 `HAND_ALREADY_FINISHED`가 났지만 `[핸드 시작]`이 실제로는 성공할 수 있는
   경우에도 안내가 뜬다. 그 경우 문장 첫 줄("[핸드 시작]을 누르면 정산됩니다")이 그대로 맞고,
   둘째 줄은 조건절("[핸드 시작]까지 인원 부족으로 거부되면")이므로 거짓말이 되지 않는다.
   엔진 로직을 UI에서 재구현해 예측하지 않기 위한 의도적 선택이다.

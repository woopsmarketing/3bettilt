## 0. 이 마일스톤의 핵심 구분

`prompt`가 요구한 가장 중요한 것은 기능 목록이 아니라 **두 사건을 섞지 않는 것**이다.

|                          | CORRECTION (rebase)              | QUICK NEXT HAND (skip)      |
| ------------------------ | -------------------------------- | --------------------------- |
| 의미                     | "내가 테이블을 잘못 입력했다"    | "이 핸드는 실제로 지나갔다" |
| handNumber               | **불변**                         | **+1**                      |
| 버튼 로테이션            | **없음** (버튼 지정 자체는 예외) | **정확히 1회**              |
| `skipped_hands` 감사     | 기록 안 함                       | 기록함 (`reason` 포함)      |
| completed hand 저장      | 안 함                            | 안 함                       |
| player learning          | 포함 안 함                       | 포함 안 함                  |
| dirty seat               | 추가 없음 (교체된 좌석 제외)     | 폴드하지 않은 딜인 좌석     |
| 기존 actions/cards/board | 전부 폐기 후 재구성              | 폐기                        |

이 표의 모든 행이 단위 테스트와 E2E 양쪽에 고정되어 있다.

## 1. Seat leave semantics (WP-1)

**이전**: 자리비움은 `table`만 즉시 바꾸고 진행 중인 핸드는 건드리지 않았다. UI가 양방향 모두
"다음 핸드부터"라고 표시했다 (ADR-0057).

**지금**: 자리비움은 항상 즉시다. 진행 중인 핸드가 있으면 **같은 `handNumber`, 같은 버튼으로
현재 핸드를 처음부터 다시 구성한다** (ADR-0073).

- 라인업·position badge·블라인드/안티·SB/BB·action order·양쪽 전략이 전부 재계산된다.
  직접 다시 계산하지 않는다 — 폐기 후 `engineStartHand`를 다시 태우면 기존 파이프라인이 전부 처리한다.
- 진행 중 핸드의 이벤트 로그를 **부분 수정하지 않는다.** 좌석만 빼내면 산술은 맞지만 실제로
  일어난 적 없는 히스토리가 만들어진다. 전부 버리고 다시 만든다.
- 재딜이 불가능하면(딜인 2명 미만 등) 정정된 테이블은 유지하고 엔진의 거부를 그대로 노출한다.
  오류를 삼키지 않고, 딜을 성사시키려고 라인업을 지어내지 않는다.
- 확인 대화상자 없음. 대신 dismissable 알림 한 줄:
  `좌석 변경으로 현재 핸드를 처음부터 다시 구성했습니다.`
- `SeatOccupancyToggleTiming`과 "다음 핸드부터" 문구는 코드에서 제거되었다.

**같은 rebase를 타는 것**: 플레이어 교체(WP-2), 빈 좌석 착석, 버튼 지정(WP-6),
그리고 리뷰 이후 추가된 **스택 정정**(ADR-0078(a), §6 참조).

## 2. Player replacement semantics (WP-2)

모든 좌석에서 `플레이어 변경`을 항상 쓸 수 있다 (빈 좌석 포함).

- **기존 플레이어 선택**: 검색 가능한 dropdown. 입력 없이 열면 전체 브라우즈.
  이 세션의 다른 좌석에 이미 앉은 플레이어는 비활성화되고 사유가 표시된다.
  최종 권한은 서버(`PLAYER_ALREADY_SEATED`)에 있고 UI는 미러링한다.
- **새 플레이어 추가**: nickname + external HUD 10개 필드를 즉시 입력.
- **빈 좌석에 착석**: 시작 스택 입력이 **필수**다. 이전에 앉아 있던 사람의 스택을 새 사람의
  것으로 물려주지 않는다 — 그건 값을 지어내는 것이다.
- 플레이어 identity는 `resolvePlayer`의 normalize-then-reuse 경로를 재사용한다. 두 번째
  identity 시스템을 만들지 않았고, 닉네임 중복은 곧 같은 플레이어다.
- 저장 직후: player 생성/재사용 → external HUD 스냅샷 append → 좌석 연결 →
  Player Profile 갱신 → **ADAPTIVE만 recompute**(`adaptiveStore.upsertInput`).
- 진행 중 핸드가 있으면 rebase.
- **교체된 좌석은 dirty가 된다** — 새로 앉은 사람의 스택은 알 수 없다.
  빈 좌석에 앉힌 경우는 사용자가 방금 실제 값을 입력했으므로 dirty가 아니다.

### 리뷰가 잡은 것 (ADR-0079)

`새 플레이어 추가`에 **기존 닉네임**을 넣으면 그 플레이어가 재사용되고, 방금 입력한 2~3개
스탯만 담긴 스냅샷이 최신이 되어 **10개 스탯 프로필이 그 몇 개로 붕괴**했다. ADAPTIVE는 최신
스냅샷 하나를 통째로 읽고 키 단위 병합을 하지 않기 때문이다(ADR-0069). 이력은 insert-only라
남아 있었지만, ADAPTIVE가 실제로 읽는 것은 효과 프로필이므로 이력 보존만으로는 부족했다.

**지금**: 요청이 `requireNew`를 싣는다. `새 플레이어 추가`에서 온 닉네임이 정규화 후 기존
플레이어에 매칭되면 **거부**하고(`PLAYER_EXISTS`) 목록에서 고르라고 안내한다. 목록에서 고르면
전체 프로필이 유지되고, 숫자를 고치는 올바른 자리는 WP-3의 값이 채워진 편집 폼이다.
닉네임 재사용은 세션 설정·일괄 임포트·목록 선택에서 그대로 옳고, 바뀌지 않았다.

## 3. Quick HUD entry (WP-3)

`PlayerProfilePanel`에서 external HUD 10개 필드
(VPIP / PFR / 3Bet / Fold to 3Bet / CBet / Fold to CBet / Steal / Check-Raise / WTSD / WSD)를
바로 고칠 수 있다.

- **UPDATE 금지 — 항상 새 스냅샷 append.** insert-only 트리거를 우회하지 않고, 사용자가 입력한
  원문(`enteredText`)은 절대 덮어쓰지 않는다.
- **빈 값은 행 자체가 생략**된다. 0으로 저장되지 않고 0으로 표시되지 않는다. 폼과 서비스
  두 층에서 각각 걸러진다.
- `sampleN`은 항상 `null`이다 — 이 소스는 핸드 수를 보고하지 않으므로 모른다고 말한다.
- ADAPTIVE는 항상 최신 스냅샷을 쓴다. 저장 직후 **ADAPTIVE만** recompute되고
  **REFERENCE는 bit-identical**이다.
- 수동 HUD(MANUAL_HUD)와 external HUD 섹션은 ADR-0069대로 분리된 채로 둔다.
- 수기 입력값은 ADR-0067의 `EXTERNAL_HUD` 시맨틱(LIFETIME, 고정 신뢰도, 스탯별 우선순위)을
  그대로 쓴다 — `prompt`가 명시적으로 요구한 것이다 (ADR-0076).

## 4. Quick-next-hand semantics (WP-4)

버튼: `빠른 다음 핸드`
설명: `남은 액션은 기록하지 않고 다음 핸드로 이동합니다. 상대 스택은 다음 핸드 전에 확인하세요.`

- 진행 중 핸드를 폐기하고, completed hand로 저장하지 않고, player learning에 넣지 않고,
  strategy trace를 만들지 않는다.
- `handNumber` +1, 버튼 로테이션 **정확히 1회**.
- `skipped_hands`에 감사 행을 기록한다. **`reason`이 추가되었다**
  (`QUICK_SKIP` | `HERO_FOLDED_UNOBSERVED`, additive 마이그레이션 `0009`).
  사유는 메뉴에서 고르는 것이 아니라 view에서 파생된다 — 히어로가 딜인되어 있고 skip 시점에
  FOLDED면 `HERO_FOLDED_UNOBSERVED`. 그래서 실제로 일어난 일과 어긋날 수 없다.
  `0009` 이전 행은 영구히 `NULL`이며 "사유가 기록되지 않음"을 뜻한다. 소급 추정하지 않는다.

## 5. Dirty stack design (WP-4/WP-5)

`prompt`는 accounting을 가정하지 말고 **검토하라**고 요구했다. 검토 결과는 취향이 아니라
엔진에 대한 사실이다:

- **폴드한 좌석**은 이 핸드의 총 기여(블라인드·안티 포함)가 팟에 들어가 되돌아오지 않는다.
  uncalled-bet 반환은 마지막 공격자에게만 발생하고, 마지막 공격자는 정의상 폴드하지 않았다.
  따라서 종료 스택은 **정확히** `startingStack − totalContribution`이다. **dirty 아님.**
- **폴드하지 않은 딜인 좌석**(올인 포함)은 결과를 모른다. 스택 불변, **dirty**.
- **딜인되지 않은 좌석**은 손대지 않는다.

히어로 특례는 없다. 계산은 `Money.sub`로만 하고 엔진의 `totalContribution`
(`packages/poker-core/src/state.ts` — 핸드 전체, `RETURN_UNCALLED` 반영)을 읽는다.
스트리트별 값을 쓰지 않는다. 음수가 나오면 clamp하지 않고 전이 전체가 실패한다.

**알려진 귀결(의도됨)**: 폴드 좌석의 칩은 빠지지만 그 팟은 분배되지 않고 버려지므로 테이블
총 칩이 감소한다. "나머지를 관찰하지 않았다"는 사실의 정직한 표현이며, dirty 좌석을 사용자가
실제 값으로 채우는 순간 해소된다. 이 핸드는 저장되지도 학습되지도 않으므로 영구 기록을
오염시키지 않는다.

**리뷰가 잡은 것 (ADR-0078(b))**: 미확인 스택은 DB에 저장되는데 dirty 표시는 메모리에만
있었다. 새로고침하면 미확인 금액이 아무 경고 없이 확인된 것처럼 렌더됐다.
→ `session_seats.stack_unverified`를 additive 마이그레이션 `0010`으로 추가해 좌석과 함께
저장·복원한다. 새로고침해도 `확인 필요` 배지가 살아 있다.

## 6. Manual stack resync (WP-5)

- SeatCard의 스택 숫자를 클릭하면 그 자리에서 inline 편집이 된다. 별도 패널이 필요 없다.
- 소수 BB 입력 → milliBB 안전 변환. **0 이하·비정수·파싱 불가는 클라이언트가 서버와 똑같이
  거부한다** (과거에 실제로 발생한, 클라이언트만 통과시켜 세션을 못 쓰게 만든 결함의 재발 방지).
- dirty 좌석에는 `확인 필요` 배지와 눈에 띄는 입력이 붙는다.
- **Enter로 확정하면 다음 dirty 좌석 입력으로 자동 포커스가 이동**한다. 마지막을 끝내면 놓아준다.
  4~5명을 몇 초 안에 처리할 수 있다.
- 값은 서버에 저장되어 **새로고침 후에도 유지**된다 (ADR-0075). 완료된 핸드(`hands` /
  `hand_events`)나 분석 스냅샷은 절대 다시 쓰지 않는다.

### 리뷰가 잡은 것 (ADR-0078(a)) — 이 마일스톤의 가장 큰 결함

두 리뷰가 독립적으로 같은 것을 재현했다. 진행 중인 핸드에서는

- 화면은 `view.stack`(핸드 내 잔여)을 보여주는데 입력창은 `table.stack`(핸드 시작 전)으로 채워졌고,
- 정정은 화면에 반영되지 않았으며,
- 다음 정산에서 `applyHandResult`(또는 quick skip의 폴드 좌석 계산)가 파생값으로 덮어썼다.

즉 **사용자가 입력한 숫자가 파생된 숫자에 파괴**되고, 살아남는 쪽은 파생값이었다 —
`CLAUDE.md` rule 3 위반. 수정 전 코드에서 실패하는 테스트로 재현을 고정했다
(`expected 100820 to be 42820`).

**지금**: 스택은 라인업의 일부다. 진행 중이면 다른 정정들과 **같은 rebase**를 탄다.
잘못된 스택으로 딜된 핸드는 딜 시점부터 잘못된 것이므로 핸드를 잃는 것이 옳다.
값 검증은 rebase보다 먼저 일어나므로 거부된 입력이 핸드를 죽이지 않는다.

정산 대기 중인 **COMPLETE 핸드**에 대한 정정은 거부한다(`HAND_ALREADY_FINISHED`) — 그 창에서는
rebase가 답이 될 수 없고(완료된 핸드는 실제 결과다) 허용하면 같은 파괴가 재현되기 때문이다.
같은 조사에서 `replaceSeatPlayer`가 COMPLETE 핸드의 dealt-in 좌석에 대해
`HAND_TABLE_MISMATCH`로 **영원히 정산되지 않는 상태**를 만들 수 있다는 것도 드러나, 진입 자체를
막았다. dealt-in이 아닌 좌석은 정산이 방문조차 하지 않으므로 계속 허용한다.

## 7. Button / position resync (WP-6)

- SeatCard의 `[버튼으로 지정]` 유지. 진행 중이면 rebase하며 SB/BB/position이 전부 재계산된다.
- 이전 구현의 `discardHand()` 선행 호출을 제거했다 — 이제 이중 폐기가 되어 재딜을 막았다.
- 버튼 좌석은 서버에 저장되어 새로고침 후에도 유지된다.

**리뷰가 잡은 것 (ADR-0078(c))**: 버튼 좌석을 진행 중에 자리비움하면 딜 시점 규칙
(ADR-0058(c))이 버튼을 시계방향으로 전진시키고 그 결과가 테이블에 커밋된다. 그 좌석을 다시
앉혀도 버튼은 **돌아오지 않는다.**

딜 규칙을 두 개로 만들지 않기로 했다 — 전진 자체는 그대로 둔다. 대신 **재구성 알림이 버튼이
어느 좌석으로 옮겨졌는지 말한다.** 사용자가 잘못된 버튼으로 핸드를 치르고도 모르는 것,
그 조용함만이 허용 불가였다. 복구 경로는 `[버튼으로 지정]`이며 그것이 WP-6이 존재하는 이유다.

## 8. Dual strategy panel (WP-7 / WP-9)

- **REFERENCE/ADAPTIVE 모드 탭을 제거**했다. Hero decision에서는 두 섹션이 항상 동시에 보인다.
- 델타는 **새로 계산하지 않는다** — 도메인이 이미 갖고 있다:
  `AdaptiveAction.deltaBps`(부호 있는 bps) → `BET +4%p`,
  `AdaptiveSizing.fromBucketIndex/toBucketIndex/bucketDelta` + from/to 금액 → `50% → 67% POT`.
  델타가 0이면 `변화 없음`으로 정직하게 표시한다.
- 엔진이 실제로 만든 단위만 표시한다. 존재하지 않는 %를 지어내지 않는다.
- 상대 데이터가 없으면 `상대 데이터 없음` / `→ 기본전략과 동일`만 표시하고 **숫자를 하나도
  렌더하지 않는다.** 가상의 상대 통계를 만들지 않는다.
- "왜 이렇게 바뀌었나요?" 문장은 `AdaptiveReasonKey` / `AdaptiveCapId` / `AdaptiveNoteCode`를
  `copy.ts`의 exhaustive Record로 옮긴 것이다. `adaptive-core`는 문장을 만들지 않는다.
- **REFERENCE 계산 경로는 바뀌지 않았다.** REFERENCE는 렌더 밖에서, ADAPTIVE는 `useMemo`로
  계산하는 기존 분리를 유지한다. "HUD 저장이 REFERENCE를 재계산하지 않는다"는 기존 테스트가
  그대로 통과한다.

**WP-9**: `rightPanelFor`가 좌석 선택을 최우선으로 둬서 **좌석을 클릭하면 전략이 사라졌다**.
`rightPanelLayoutFor`가 `{ lead, drawer }`를 돌려주도록 바꿔, hero가 액터면 전략이 리드하고
선택된 좌석의 프로필은 **전략 아래 drawer**로 함께 열린다 (ADR-0077).
`heroIsActor === true`인 **입력 공간 전체**에 대해 `lead === 'STRATEGY'`임을 테스트가 강제하므로,
"좌석을 클릭했더니 전략이 사라졌다"는 상태는 이제 표현 불가능하다.

## 10b. 재검증 라운드 (R2)

수정 라운드 뒤 **독립 재검증**을 한 번 더 돌렸다. 리뷰 보고서를 믿지 말고 원래 재현 절차를 다시
실행하라는 지시였고, 결과는 **11 CLOSED / 3 PARTIAL / 신규 3건**이다.

CLOSED는 전부 관찰로 뒷받침되었다. 예: 진행 중 스택 정정은 이제 rebase되어 정산 후에도 42000이
살아남고(이전엔 100820으로 파괴), `새 플레이어 추가`의 닉네임 4가지 변형이 전부 거부되며 그 뒤
스냅샷 1개·10개 스탯 프로필이 그대로였고, dirty 배지는 **실제 브라우저 새로고침**을 통과했다.

PARTIAL 3건 중 버튼 왕복 미복원은 ADR-0078(c)가 승인한 동작이며 "조용함"만 닫힌 것이다.

### 재검증이 찾은 신규 결함 3건 — 2건은 우리가 만든 회귀

1. **트레이 floor가 짧은 뷰포트에서 좌석을 덮었다.** 팔레트 잘림을 고치면서 floor를 152px →
   296px로 **무조건** 올린 것이 원인. 1024×600에서 히어로 스택 숫자가 `entry-tray`로 hit-test되고,
   1280×560에서는 팔레트가 닫혀 있어도 키보드 힌트가 좌석을 덮었다.
2. **좁은 폭에서 2(deuce) 네 장을 마우스로 클릭할 수 없었다.** 큰 카드로 전환하는 지점이
   `sm:`(640px)이라 너무 낮아 그리드가 컨테이너를 조용히 넘쳤고 가로 스크롤이 없었다.
   **E2E가 이것을 잡지 못한 이유는 Playwright의 `.click()`이 `scrollIntoViewIfNeeded`를 부르기
   때문이다** — 사용자에게는 그런 것이 없다. 그래서 R2부터 레이아웃 판정은 `.click()` 성공이 아니라
   `document.elementFromPoint` 실측으로 한다.
3. **막다른 상태에서 두 오류가 서로를 가리켰다.** 헤즈업 파산 후 `startHand()`는
   `NOT_ENOUGH_PLAYERS`, `correctSeatStack`은 "핸드를 시작해 정산하라"고 안내했다 — 성공할 수 없는
   유일한 행동이다. (막다른 상태 자체는 이번 마일스톤이 만든 것이 아니다. 이전에는 값이 쓰였다가
   파괴되는 쪽이었다.)

### R2 수정 결과

- 트레이는 `min-h = max-h = min(18.5rem, calc(100vh − 26.5rem))`. `26.5rem`은 실측(헤더 59 + 독 61 +
  펠트 304)에서 나온 값이고, floor와 cap이 같으므로 팔레트 열림·닫힘 사이 트레이 높이가 **정확히
  동일**하다(ADR-0054의 no-jump 유지). 어워드 패널만 예외적으로 cap을 연다.
- 카드 크기는 기본 44×52, `min-width:1152px and min-height:680px`에서 56×64. 두 숫자 모두 실측에서
  역산했다.
- 스크롤 가시화: `scrollbar-color`만으로는 Chromium이 오버레이 스크롤바를 유지해
  `offsetWidth == clientWidth`였다. `scrollbar-gutter: stable`을 더해 11px을 실측으로 확보했다.
- 7개 뷰포트 × 팔레트 열림·닫힘 전부에서 **좌석 덮임 0, 도달 불가 카드 0, 문서 스크롤 0,
  독은 항상 뷰포트 안, 그리드 가로 넘침 0**.
  스크롤 없이 52장이 전부 보이는 것은 1024×640 이상. 1024×600 / 1280×560은 요구 높이(644px)가
  화면보다 커서 물리적으로 불가능하며, **양보하는 쪽은 팔레트이고 좌석과 독은 절대 아니다** —
  나머지 카드는 보이는 스크롤바로 도달한다.
- 막다른 상태 안내는 실제로 통하는 출구(칩이 0인 좌석의 자동 리바이, 또는 빈 좌석에 착석)를
  이름으로 말하고, 브라우저에서 그 출구를 따라가 실제 딜까지 성공함을 확인했다.

## 11. Limitations — 알려진 한계 (전부 의도적이거나 기록됨)

1. **rebase는 진행 중인 핸드를 잃는다.** 부분 mutation보다 낫다는 판단이지만, 액션을 많이
   입력한 뒤 좌석을 고치면 다시 입력해야 한다. ADR-0073의 명시적 트레이드오프다.
2. **버튼 왕복은 복원되지 않는다.** 버튼 좌석을 진행 중에 자리비움하면 버튼이 전진하고,
   다시 앉혀도 돌아오지 않는다. 이제 알림이 그 사실을 말하고 `[버튼으로 지정]`이 복구 경로다.
   딜 규칙을 두 개로 만들지 않기 위한 선택이다 (ADR-0078(c)).
3. **quick skip 후 테이블 총 칩이 감소한다.** 폴드 좌석의 기여는 빠지지만 팟은 버려진다.
   §5 참조 — 의도된 정직한 표현이며 dirty 좌석 정정으로 해소된다.
4. **`stack_unverified`는 `DROP COLUMN`으로 되돌릴 수 없다.** SQLite가 CHECK가 참조하는
   컬럼을 지우지 못한다. 이 저장소에 down-migration이 없어 정보성이며, 마이그레이션 헤더에 기록했다.
   `0009`도 같다.
5. **`updateSessionTable`은 `stack_unverified`를 쓰지 않는다.** 전체 `TableState`를 받는데
   `TableState`에는 "사람이 확인했는가"라는 개념이 없어 값을 지어내야 하기 때문이다.
   현재 `apps/web`에서 호출되지 않으며, 스택을 옮기는 경로에 연결되면 낡은 표시가 남을 수 있다.
   함수 주석에 기록되어 있다.
6. **`SeatCard`의 중첩 interactive ARIA.** inline 스택 입력을 담기 위해 루트가
   `<button>` → `<div role="button">`이 되었다. 클릭·키보드(Enter/Space) 선택은 회귀 테스트로
   고정했지만, `role="button"` 요소가 실제 `<button>`을 자식으로 가지므로 보조기술이 내부
   버튼을 노출하지 않을 수 있다. 알려진 이슈로 파일 헤더에 기록.
7. **높이 620px 이하 뷰포트에서 펠트가 매우 얇아진다.** 이번 변경 이전에도 같았고 나빠지지
   않았다. 액션 독은 어떤 경우에도 뷰포트 안에 있다.
8. **`PLAYER_EXISTS` 안내가 구조화 필드를 쓰지 않는다.** 서버 메시지를 파싱하는 대신 입력한
   닉네임으로 검색을 프리필한다. 결과에 `matchedPlayerId`가 있으면 한 번에 좁힐 수 있다.
9. **E2E가 커버하지 않는 것**: 빈 좌석에 새 플레이어를 앉히는 전체 경로, 서버 저장 실패 배너 경로.
   둘 다 단위/컴포넌트 테스트로는 커버된다.
10. **E2E의 정확 스택 주장(99.84 / 99.34 BB)은 안티 정책에 결합**되어 있다. 정책이 바뀌면
    의도적으로 깨진다.
11. **ADAPTIVE E2E는 `data-changed=true`를 주장하지 않는다.** 정책 상수를 튜닝할 때마다 깨지는
    것을 피하기 위해서다. 믹스 산술은 `adaptive-core` 스위트가 소유한다.
12. **560~600px 높이 뷰포트에서는 팔레트에 세로 스크롤이 필요하다.** 좌석 그리드(304px) + 헤더 +
    독 + 팔레트를 다 넣으려면 644px이 필요한데 화면이 그보다 작다. 양보하는 쪽은 팔레트로 정했고,
    좌석과 액션 독은 어떤 경우에도 양보하지 않는다. 해소하려면 좌석 카드 아래 컨트롤 높이를 줄여
    펠트 요구를 낮추는 별도 작업이 필요하다.
13. **`scrollbar-gutter: stable`은 Chromium에서만 실측**했다. Firefox/Safari는 측정하지 않았다.
14. **막다른 상태 안내는 관측으로 상태를 인식한다** — 엔진 오류 코드와 COMPLETE 대기 여부를 읽는다.
    엔진 로직을 UI에 다시 구현하지 않기 위한 선택이고, `[핸드 시작]`이 성공 가능한 경우에도 뜰 수
    있으나 문장이 조건절이라 거짓이 되지는 않는다.
15. **`packages/strategy-core/src/postflop/benchmark.test.ts`는 부하에 민감하다.** 격리 실행에서는
    4/4 통과하지만 전체 스위트 병렬 실행 중 7회 중 1회 실패한 것이 관측되었다. 지연 시간을 직접
    비교하는 테스트라 병렬 부하가 측정을 왜곡한다. 이번 마일스톤 이전부터 있던 성질이다.
16. **부분 프로필 붕괴 메커니즘은 서버 계층에 여전히 살아 있다.** `requireNew: false`로 현재 착석자에
    대해 부분 `externalHud`를 보내거나 `saveExternalHudSnapshot`에 부분 항목을 보내면 최신 프로필이
    그만큼으로 줄어든다. UI에서는 도달 불가능하다 — 스왑 패널은 NEW 모드에서만 `externalHud`를 보내고,
    프로필 패널은 최신 스냅샷으로 폼을 미리 채워 한 필드 수정이 나머지를 떨어뜨리지 못하게 한다.
    서버 액션은 공개 엔드포인트이므로 이 방어는 UI 쪽에만 있다. 로컬 단일 사용자 앱이라 이 정도로
    두었고, 서버 측 방어가 필요해지면 별도 결정이 필요하다.

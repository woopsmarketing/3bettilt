## 1. 무엇이 원본(raw) 히스토리로 저장되는가

핸드 하나가 끝나면, **그 핸드에서 실제로 일어난 일 전부**가 저장됩니다. 요약이나 통계가 아니라
"사건의 목록" 자체입니다.

| 저장되는 것 | 설명 |
| --- | --- |
| 핸드 헤더 (`hands`) | 세션 id, 핸드 번호, 시작/종료 시각, `source`(항상 `MANUAL_PRACTICE`), `schema_version` |
| 참가 라인업 (`hand_players`) | 그 핸드에 실제로 딜인된 좌석, 좌석별 포지션과 시작 스택, 연결된 플레이어 id |
| 이벤트 로그 (`hand_events`) | `HAND_STARTED`부터 `HAND_FINISHED`까지 **순서 그대로**의 모든 사건 — 블라인드 포스팅, 모든 액션(폴드/체크/콜/벳/레이즈/올인)과 금액, 보드 카드, `HOLE_CARDS_SET`(히어로 입력과 SHOW 공개 둘 다), 팟 분배, 언콜드 벳 반환, 레이크, 수수료 |

핵심 성질 두 가지입니다.

- **금액은 전부 정수 milliBB로 저장됩니다.** 분할 팟의 각 몫, 반환된 언콜드 벳, 레이크, 수수료가
  전부 정확한 정수로 왕복(round-trip)됩니다 (`C0C1_WP_C0B.md` 테스트 8).
- **파생값은 저장하지 않습니다.** 최종 스택 같은 값은 헤더에 중복 기록하지 않습니다 — 이벤트 로그가
  권위(authoritative)이고, 그걸 접으면(fold) 최종 상태가 그대로 재현되기 때문입니다 (ADR-0039,
  ADR-0059g).

## 2. 저장 경계(persistence boundary)는 정확히 어디인가

**핸드가 `phase === 'COMPLETE'`가 되는 그 순간, 딱 한 번.** (ADR-0059b)

- 트리거는 `apps/web/src/components/table/useCompletedHandSaves.ts`의 React `useEffect`입니다.
  스토어(`tableStore.ts`)는 **전혀 수정되지 않았습니다** — 포커 엔진과 스토어는 네트워크의 존재를
  모릅니다.
- 서버 액션은 **await 하지 않고** 발사됩니다. 즉 저장이 느리거나 실패해도 다음 핸드 시작(`핸드 시작`)이
  막히지 않습니다. "저장이 끝나지 않은 프로미스"로 이걸 증명하는 테스트가 있습니다
  (`HandHistorySave.test.tsx` 테스트 7).
- 전송되는 것은 **가공되지 않은 이벤트 로그 + 세션 id + 클라이언트 시각 2개**뿐입니다. 서버는 그 로그를
  엔진 코덱으로 다시 디코드하고, 엔진으로 다시 접어서(fold) 상태를 **재계산**합니다. 클라이언트가
  계산한 결과는 아무것도 믿지 않습니다.
- 서버가 거부하는 경우: 로그가 `COMPLETE`로 끝나지 않으면 `HAND_NOT_COMPLETE`, 디코드 불가면 거부,
  존재하지 않는 세션이면 `NOT_FOUND`.
- **닫힌(CLOSED) 세션도 받아들입니다.** 이미 일어난 역사를 거부하면 실제로 플레이한 핸드가
  사라지기 때문입니다 (CLAUDE.md 규칙 3).
- 시각은 거부하지 않고 **클램프(clamp)** 합니다. 사용자의 시계가 틀렸다고 해서 핸드를 잃으면 안 됩니다.

실패하면 화면에 빨간 배너가 뜹니다: `핸드 N 기록 저장 실패 (<code>: <message>). 이 핸드는 아직
저장되지 않았습니다.` + `재시도` 버튼. 조용히 삼키지 않습니다.

## 3. 왜 이번 마일스톤은 "완료된 핸드"만 영구 저장하는가

진행 중인 핸드를 매 액션마다 DB에 추가로 쓰는(incremental append) 방식은 훨씬 큰 작업입니다.
리로드 복구, 부분 로그 복원, 중간 상태 정합성까지 다뤄야 하고, 그건 Phase 8의 범위입니다.

이번에 `COMPLETE` 한 지점만 고른 이유:

1. 그 시점에 **모든 것이 최종**입니다 — 팟 분배, 레이크, 수수료, `HAND_FINISHED`까지. 즉 나중에
   수정할 이유가 원천적으로 없습니다. 그래서 §4의 "한 번 쓰면 불변" 규칙이 성립합니다.
2. C1(학습)이 필요로 하는 것은 **끝난 핸드**뿐입니다. 진행 중인 핸드는 통계의 입력이 될 수 없습니다.
3. 액션 경로가 동기적(synchronous)이라는 ADR-0043의 규칙을 건드리지 않습니다.

**대가**: 핸드 도중에 페이지를 새로고침하면 그 진행 중 핸드는 여전히 사라집니다. 이건 ADR-0059가
명시적으로 받아들인 한계이며 화면에도 그렇게 안내됩니다.

## 4. 데이터베이스 스키마 (0004 / 0005 마이그레이션과 트리거 보호)

### 4.1 마이그레이션 0004 — `0004_completed_hand_history.sql`

기존 `hands` 테이블에 **컬럼 2개를 추가**하고 **트리거 6개**를 겁니다. 테이블을 다시 만들지 않습니다.

- `hands.source` — `'MANUAL_PRACTICE' | 'MANUAL_REVIEW'`, 기본값 `MANUAL_PRACTICE`
- `hands.schema_version` — 정수 ≥ 1, 기본값 1 (저장 표현이 미래에 진화할 때를 위한 표식)

> 참고: drizzle-kit 자동 생성 SQL은 이 경우 SQLite의 "테이블 통째로 재생성" 방식을 뽑아내는데,
> 그 방식은 `DROP TABLE hands`를 포함하고 트랜잭션 안에서는 FK 캐스케이드가 꺼지지 않아
> `hand_events` / `hand_players`가 전부 날아갑니다. 그래서 이 마이그레이션은 **손으로 작성한
> `ALTER TABLE ... ADD COLUMN`** 으로 대체되었습니다 (`C0C1_WP_C0B.md` §1).

**트리거 6개 (ADR-0060 — 원본 히스토리 불변성):**

| 트리거 | 언제 | 효과 |
| --- | --- | --- |
| `hand_events_no_update` / `hand_events_no_delete` | 모든 UPDATE / DELETE | 무조건 거부 |
| `hand_players_no_update` / `hand_players_no_delete` | 모든 UPDATE / DELETE | 무조건 거부 |
| `hands_no_update_once_finished` | UPDATE, `WHEN OLD.finished_at IS NOT NULL` | 끝난 핸드는 수정 불가 |
| `hands_no_delete` | 모든 DELETE | 무조건 거부 |

`hands`를 지울 수 없으므로 `hand_events`/`hand_players`로 가는 `ON DELETE CASCADE`는 **도달
불가능**합니다. 즉 "실수로 세션을 지웠더니 히스토리가 같이 날아갔다"는 시나리오가 구조적으로
존재하지 않습니다. 수정은 덮어쓰기가 아니라 **새 기록으로의 승계(supersession)** 로만 가능합니다.

### 4.2 마이그레이션 0005 — `0005_analysis_and_model_snapshots.sql`

**새 테이블 7개 + 손으로 작성한 트리거 14개** (7개 테이블 × UPDATE/DELETE 각 1개). 전부 insert-only입니다.

| 테이블 | 담는 것 |
| --- | --- |
| `analysis_runs` | 분석 실행 1회의 헤더: 세션, 시작/종료 시각, 알고리즘 버전, `SUCCESS/PARTIAL/FAILED`, 핸드·플레이어·관찰·SHOW 카운트 |
| `analysis_run_players` | 그 실행에서 플레이어별 결과: `SNAPSHOT_CREATED / NO_CHANGES / FAILED`, 실패 사유 |
| `player_model_snapshots` | 스냅샷 헤더: `model_version`, `input_hash`, `algorithm_version`, 소스 핸드/관찰/SHOW 수, 신뢰도 설정(`k`, 두 임계값) |
| `player_model_stats` | 글로벌 스탯 행(VPIP, PFR, …): `stat_key`, `position`(nullable), `opportunities`, `actions` |
| `player_spot_stats` | 상황별 통계: `spot_key` + 서술자 컬럼 전부, 기회 수, effect 5종 / verb 6종 카운트 |
| `player_model_bet_sizes` | 벳 사이즈 관찰: 원본 milliBB 5개 값 + 버킷 라벨 |
| `player_model_show_evidence` | SHOW로 실제 공개된 카드 증거 |

중요한 제약 몇 가지:

- `UNIQUE(player_id, model_version)` — 버전이 절대 덮어써지지 않는다는 **진짜 보증**.
- `analysis_run_players`: `snapshot_id IS NOT NULL` ⟺ `outcome = 'SNAPSHOT_CREATED'` (CHECK).
  "스냅샷을 만들었다"고 주장하면서 스냅샷이 없는 행은 DB가 거부합니다.
- `player_spot_stats`: `sum(effects) = opportunities`, `sum(verbs) = opportunities` CHECK.
- `player_model_stats`: `actions ≤ opportunities` CHECK. 부분 유니크 인덱스 2개로 `position = NULL`
  버킷과 6개 포지션 버킷을 **별개**로 유지합니다 (ADR-0035 — 절대 합산하지 않음).
- 모든 금액/카운트/시각 컬럼에 `typeof(col) = 'integer'` + 범위 CHECK (ADR-0041).
- `player_observations`(사용자가 손으로 입력한 관찰)는 **분석이 절대 쓰지 않습니다** (ADR-0062a).
  0005 업그레이드 테스트가 그 행들이 바이트 단위로 그대로임을 확인합니다.

### 4.3 트리거 총계와 안전장치

0001의 6개 + 0004의 6개 + 0005의 14개 = **총 26개**. `packages/db/tests/insert-only.test.ts`가
이 26개를 **전부 나열해서** 고정(pin)합니다. drizzle-kit은 트리거를 생성하지 않으므로, 보호되지 않은
새 테이블이 생기면 이 테스트가 실패해서 알려주는 것이 유일한 감시 장치입니다.

### 4.4 실제 DB 사본 검증

두 마이그레이션 모두, 사용자의 **실제 `.data/gto-self.db` 사본**에 적용해 검증했습니다. 원본 파일은
한 번도 열지 않았고 크기·수정시각이 그대로임을 전후로 확인했습니다. 결과: 모든 기존 행이 바이트 단위로
동일, `integrity_check` = ok, `foreign_key_check` = 비어 있음, `__new%` 임시 테이블 없음.
(실제 DB에는 아직 핸드가 0건이므로 — C0-A 감사의 핵심 발견 — 핸드가 들어 있는 상태의 업그레이드는
테스트가 직접 구성한 DB로 검증했습니다. 둘 다 통과.)

## 5. 이벤트 직렬화 / 재생(replay) 설계

- 클라이언트는 `encodeHandEvents(hand.events)`로 엔진의 이벤트 로그를 그대로 직렬화해 보냅니다.
- 서버는 `decodeHandEvents` → `loadHand`(구조적 fold)로 **다시 재생**해 상태를 얻습니다. 이게
  권위 있는 상태이고, 클라이언트가 보낸 어떤 요약도 신뢰하지 않습니다.
- 저장 시 각 이벤트는 `seq`(순서), `kind`, `commandSeq`와 함께 행으로 들어갑니다. 읽을 때는 삽입
  순서가 아니라 `seq` 컬럼 기준으로 정렬됩니다.
- 왕복 검증: 저장 후 다시 읽어 만든 핸드의 `events`와 `state`가 원본과 **완전히 동일**하다는 테스트가
  db 계층과 web 계층 양쪽에 있습니다 (`C0C1_WP_C0B.md` 테스트 5, `C0C1_WP_C0C.md` 통합 테스트 1).
- 분석은 이 재생 결과만 읽습니다. 즉 **원본 로그 하나가 유일한 진실**이고, 통계는 언제든 거기서
  다시 만들어낼 수 있습니다.

## 6. 정확히 한 번(exactly-once) 설계 — B1 리로드 버그 수정 포함

### 6.1 두 겹의 방어

**클라이언트 쪽 (선제 차단):** `handId` 하나당 `SaveEntry` 하나를 ref에 들고, 상태를
`PENDING → IN_FLIGHT → SAVED | FAILED`로 관리합니다. 발사 직전에 항상 검사하므로 —
리렌더, React Strict Mode의 이중 effect, 연속 `다음 핸드`, 진행 중 요청과 경쟁하는 재시도 — 이
다섯 가지 위험이 전부 하나의 가드로 막힙니다.

**서버/DB 쪽 (진짜 보증):** `hands.id`가 기본키이고, 그 값은 **엔진이 `HAND_STARTED`에서 만든
안정적인 `handId`** 입니다. 저장 전에 그 id로 먼저 조회해서:

- 같은 핸드가 이미 있으면 → `ALREADY_PERSISTED`, **아무것도 쓰지 않음** (성공으로 취급)
- 같은 id인데 내용이 다르면 → `CONFLICT` (어느 필드가 다른지 명시)

무결성 확인은 세 가지 싼 비교(세션 id, 핸드 번호, 이벤트 개수)입니다. 이건 체크섬이 아니라
**id 충돌 감지용 감시선**이며, 그렇게 문서화되어 있습니다.

### 6.2 B1 — 리로드 후 핸드가 영구히 저장 불가능했던 버그 (BLOCKER, 수정 완료)

독립 리뷰(R1)가 찾아낸 유일한 블로커입니다. 내용은 이렇습니다.

- `hands`에는 `UNIQUE(session_id, hand_number)`가 걸려 있습니다.
- 핸드 번호는 메모리 상의 테이블 상태(`TableState.handNumber`)에서 나오는데, 그 값은 **세션 생성
  시점에 딱 한 번** DB에 쓰이고 그 뒤로는 갱신되지 않았습니다.
- 그래서 **페이지를 새로고침하거나 두 번째 탭을 열면 핸드 번호가 처음부터 다시 시작**되고, 그
  뒤에 친 핸드는 유니크 제약에 걸려 **영구히 저장 실패**했습니다. 재시도해도 동일한 로그를 보내니
  똑같이 실패합니다. 게다가 `세션 분석 및 반영`은 실패한 저장을 막지 않으므로, 잘려나간 히스토리로
  조용히 분석이 돌아갈 수 있었습니다.

**수정 (3단):**

- **(a) 카운터를 핸드와 같은 트랜잭션에서 영구화.** `insertCompletedHand` 안에서
  `sessions.hand_number`를 `hand.state.handNumber + 1`로 올립니다. 조건은 `WHERE hand_number < next`
  이므로 **절대 뒤로 가지 않습니다**(늦게 도착한 낮은 번호의 저장이 표식을 되돌리지 않음). 핸드 없이
  카운터만 커밋되거나 그 반대인 경우가 원천적으로 불가능합니다.
- **(b) 세션 로드 시 최고 수위(high-water mark)에서 재개.** 새 읽기 `maxStoredHandNumber`를 만들어,
  `loadSessionView`가 `max(sessions.hand_number, max(hands.hand_number) + 1)`을 스토어에 넘깁니다.
  두 항을 모두 쓰는 이유는, 이 수정 **이전에** 만들어진 세션은 카운터가 0인 채 실제 핸드를 갖고
  있어서 저장된 핸드를 읽어야만 진짜 위치를 복원할 수 있기 때문입니다.
- **(c) 충돌을 이름 있는 에러로.** 기존 중복 검사는 `hands.id` 기준이라 "다른 핸드가 같은 번호를
  재사용"하는 경우를 볼 수 없었습니다. 이제 `(session_id, hand_number)`를 먼저 확인해
  **명명된 `CONFLICT`** (그 번호를 이미 가진 핸드 id를 알려줌)를 돌려줍니다. 원시 SQLite 드라이버
  문자열이 사용자 배너에 뜨지 않습니다.

**증명:** 4개의 db 테스트와 1개의 E2E 테스트(`리로드 후 친 핸드도 저장된다`)가 추가되었고, 수정을
되돌리면 실패한다는 것이 실제로 확인되었습니다. 수정 전에는 기존 E2E는 통과하고 새 E2E만
`hand-save-error` 1건으로 실패 — 정확히 리뷰가 지목한 그 구멍입니다.

### 6.3 분석 쪽의 정확히 한 번

버튼을 두 번 눌러도 숫자가 두 배가 되지 않습니다. 이건 §13의 `NO_CHANGES` 게이트가 담당합니다.

## 7. 플레이어 신원(identity) 설계

- 좌석에 입력한 **닉네임**을 정규화(`normalized_nickname`, UNIQUE)해서 `players` 행을 찾습니다.
  있으면 **재사용**, 없을 때만 새로 만듭니다 (`apps/web/src/server/session-service.ts`의 `resolvePlayer`).
- **퍼지 매칭 없음.** 비슷한 이름을 추측해서 합치는 일은 하지 않습니다. 오탐으로 두 사람의 히스토리가
  섞이는 것이 이름이 갈리는 것보다 훨씬 나쁘기 때문입니다.
- 그 결과 **같은 닉네임은 세션을 넘어 자동으로 같은 플레이어**가 되고, 이것이 §16 누적의 토대입니다.
- `hand_players.player_id`가 `NULL`인 좌석(신원 미상 상대)은 분석 대상 발견 쿼리에 잡히지 않습니다.
  즉 절대 분석되지 않고, 절대 실행을 실패시키지도 않습니다.
- 한 핸드의 라인업은 `dealtInSeats`(그 핸드에 실제로 딜인된 좌석)에서 나오므로, 6인 → 5인 → 4인처럼
  인원이 바뀌어도 각 핸드가 **실제로 참여한 사람에게만** 연결됩니다.

## 8. "기회(opportunity)"란 무엇인가

이 프로젝트에서 통계의 분모는 언제나 **기회(opportunity)** 이고, 기회의 정의는 딱 하나입니다.

> **포커 엔진이 그 좌석에게 실제로 차례를 준 경우** — 즉 `HandState.actions`에 그 좌석의
> `ActionRecord`가 존재하는 경우.

포지션이나 상황으로부터 "이 사람은 여기서 액션할 수 있었을 것"이라고 **추론하지 않습니다**. 엔진이
남긴 사실만 셉니다. 이 한 줄에서 다음이 자동으로 따라옵니다 (전부 테스트로 고정):

- **폴드한 사람** — 이후 `ActionRecord`가 없음 → 이후 어떤 스트리트에서도 기회 없음.
- **올인한 사람** — `seatsAbleToAct`가 건너뜀 → 이후 베팅 기회 없음. (단 쇼다운에는 갈 수 있으므로
  `WTSD`/`WSD`는 여전히 적용됩니다 — 그건 액션이 아니라 핸드에 관한 통계이기 때문입니다.)
- **자리비움(sit-out)** — `dealtInSeats`에 없음 → 아무 기록도 생기지 않고, 라인업 인원수도 실제 값 유지.
- **워크(walk, 모두 폴드해서 BB가 그냥 이김)** — BB는 액션한 적이 없음 → 기회 **0**. VPIP 분모에도
  들어가지 않습니다.
- **리므드 팟(limped pot)** — 이니셔티브 보유자가 없으므로 아무도 `CBET_*` 기회를 받지 않습니다.
  리므드 팟의 벳은 "계속 베팅(continuation)"이 아니기 때문입니다.

## 9. VPIP / PFR / 3Bet 등의 분모는 어떻게 계산되는가

21개의 `ModelStatKey` 각각이 분모(기회)와 분자(실제 행동)를 명시적으로 갖습니다. 주요 항목:

| 스탯 | 분모 (기회) | 분자 (행동) |
| --- | --- | --- |
| `VPIP` | 프리플랍에서 최소 1번 결정을 마주함 | 프리플랍 effect가 CALL / BET / RAISE 중 하나 |
| `PFR` | 프리플랍에서 최소 1번 결정을 마주함 | 프리플랍 effect가 RAISE / BET |
| `RFI` | 앞에 레이즈 0, 리므 0인 상태의 첫 프리플랍 결정 (BB 제외) | 그 결정이 RAISE |
| `STEAL_ATTEMPT` | 위 `RFI` 기회이면서 자기 포지션이 CO / BTN / SB | RAISE |
| `FOLD_TO_STEAL` | SB/BB에서 CO/BTN/SB의 오픈을 마주한 첫 `VS_OPEN` 결정 | FOLD |
| `THREE_BET` | 앞에 레이즈가 정확히 1개인 첫 프리플랍 결정 (`VS_OPEN` + `SQUEEZE`) | RAISE |
| `FOLD_TO_THREE_BET` | **내가 1번 레이즈를 했고** 이제 2번 레이즈를 마주한 첫 결정 | FOLD |
| `FOUR_BET` | 위와 **같은** 결정 | RAISE |
| `CBET_{FLOP,TURN,RIVER}` | 그 스트리트의 첫 결정 + 이니셔티브 보유 + 앞에 벳 없음 | BET |
| `FOLD_TO_CBET_{…}` | 그 스트리트에서 이니셔티브 보유자의 유일한 벳을 마주한 첫 결정 | FOLD |
| `CHECK_RAISE_{…}` | 이번 스트리트에 내가 체크했고 지금 벳을 마주한 첫 결정 | RAISE |
| `TURN_BARREL` | 플랍 c-bet 기회가 있었고 실제로 쳤으며, 턴 `CBET_TURN` 기회도 존재 | 턴 c-bet을 침 |
| `RIVER_BARREL` | 위와 같은 논리 한 단계 위 | 리버 c-bet을 침 |
| `WTSD` | 보드가 3장 이상 나왔고 프리플랍에 폴드하지 않음 | 핸드가 `SHOWDOWN`으로 끝났고 최종 상태가 `IN_HAND`/`ALL_IN` |
| `WSD` | 쇼다운에 도달함 | `wonGross > 0` |

세부 판정 몇 가지:

- 강제된 블라인드 포스팅은 VPIP가 **아닙니다** (엔진이 블라인드를 `actions`에 넣지 않습니다).
  BB가 옵션을 체크하면 "기회는 있었고 행동은 없었음"으로 기록되고, SB가 컴플리트하면 VPIP입니다.
- **3벳을 마주한 콜드콜러는 `FOLD_TO_THREE_BET`에 들어가지 않습니다.** 그건 다른 질문(스퀴즈를
  마주한 상황)이기 때문입니다. 오프너만 셉니다.
- 커버 못 하는 짧은 올인 콜은 effect가 `CALL`이고, verb는 `ALL_IN`으로 남습니다. **verb와 effect를
  둘 다 보존**합니다.
- **모든 스탯은 두 번 기록됩니다**: `position: null` 버킷 한 번, 자기 포지션 버킷 한 번. 이 둘은
  ADR-0035에 따라 **별개의 버킷이며 절대 합산하지 않습니다**. UI도 두 섹션으로 나누어 렌더링하고,
  포지션 섹션 제목에 `전체 포지션 값과 합산하지 않습니다`라고 적혀 있습니다.
- **비율은 어디에도 저장되지 않습니다.** 카운트만 저장하고, 퍼센트는 화면에서 그때 계산합니다.

## 10. 상황별(spot) 통계는 어떻게 동작하는가

"이 사람은 BB에서 BTN 오픈을 마주했을 때 뭘 하는가?" 같은 질문에 답하기 위해, 모든 결정에
**상황 키(spot key)** 를 붙입니다.

### 프리플랍 — 8개 패밀리

| 패밀리 | 조건 | 키 예시 |
| --- | --- | --- |
| `RFI` | 앞에 레이즈 0, 리므 0 (BB 아님) | `BTN_RFI` |
| `VS_LIMP` | 레이즈 0, 리므 ≥1 | `CO_VS_LIMP` |
| `BB_OPTION` | 레이즈 0, 포지션 BB | `BB_OPTION` |
| `VS_OPEN` | 레이즈 정확히 1, 콜드콜러 0 | `BB_VS_BTN_OPEN` |
| `SQUEEZE` | 레이즈 1, 콜드콜러 ≥1 | `BB_SQUEEZE_VS_CO` |
| `VS_THREE_BET` | 레이즈 2 + 내가 1번 레이저 | `HJ_OPEN_FACING_BTN_3BET` |
| `VS_FOUR_BET` | 레이즈 3 + 내가 2번 레이저 | `BTN_3BET_FACING_HJ_4BET` |
| `VS_MULTI_RAISE` | 그 외 전부 (정직한 catch-all) | `SB_VS_MULTI_RAISE` |

리므(limp)와 오픈을 섞지 않고, 아이솔레이션과 RFI를 섞지 않는 것이 핵심입니다. 섞으면 둘 다 오염됩니다.

### 포스트플랍 — 키 형태

`{street}_{family}_{position}_{relation}_{lineup}_{potType}[_{facingSize}]`
예: `TURN_FACING_CBET_BB_OOP_HEADS_UP_THREE_BET_MEDIUM`

| 차원 | 값 |
| --- | --- |
| street | FLOP / TURN / RIVER |
| family | `CBET` · `FACING_CBET` · `DONK_LEAD` · `CHECKED_TO` · `FACING_BET` · `FACING_RAISE` — **전부 "기회"의 이름이지 "행동"의 이름이 아님** |
| position | 6개 포지션 |
| relation | IP / OOP — 포지션 이름이 아니라 **살아 있는 좌석들의 실제 행동 순서**에서 계산 |
| lineup | HEADS_UP / MULTIWAY (3인·4인은 같은 버킷 — 표본이 절대 안 나옴) |
| potType | LIMPED / SINGLE_RAISED / THREE_BET / FOUR_BET_PLUS |
| facingSize | NONE · TINY ≤33% · SMALL ≤50% · MEDIUM ≤75% · LARGE ≤90% · POT ≤110% · OVERBET >110% (팟 대비 분수를 정수 교차곱으로 비교 — 부동소수점 없음) |

각 상황 버킷은 `opportunities`와 함께 **effect 5종 / verb 6종의 카운트**를 들고 있고, DB CHECK가
"두 합이 각각 기회 수와 같다"를 강제합니다.

버킷 개수는 **핸드 수와 무관하게 상수 상한**을 가집니다 — 아무리 많이 쳐도 버킷이 무한히 늘지 않습니다.

**의도적으로 넣지 않은 것:** 보드 텍스처 차원(분류기가 없고, 만들면 그건 우리가 지어낸 포커 주장이 됨 —
CLAUDE.md 규칙 7), 스택 깊이 버킷(`strategy-core`의 정의를 복제하면 조용히 갈라지는 두 번째 정의가 생김),
`CHECK_RAISE` 패밀리(같은 상황을 `FACING_CBET`이 이미 이름 붙였고, 체크레이즈 질문은 별도 글로벌 스탯으로
정확히 셈), 3-way/4-way 분리, TIGHT/LOOSE 같은 파생 형용사.

## 11. SHOW와 MUCK 처리

- **SHOW 증거는 오직** `HOLE_CARDS_SET { revealed: true }` 이벤트에서만 나옵니다 (ADR-0052, ADR-0062f).
  UI에서 이 이벤트를 만드는 경로는 쇼다운의 명시적 `오픈` 요청 하나뿐입니다.
- **히어로 자신의 카드 입력은 `revealed: false`로 하드코딩**되어 있습니다. 그래서 히어로의 카드가
  상대의 SHOW 증거로 새어 나갈 수 없습니다.
- **MUCK은 카드를 만들지 않습니다.** 머크한 좌석은 `HOLE_CARDS_SET` 이벤트를 아예 남기지 않으므로,
  쇼다운까지 간 머크 좌석의 `holeCards`는 `[]` — 폴드한 좌석과 **완전히 동일**합니다. 그럴듯한
  카드를 지어내는 코드가 존재하지 않습니다.
- SHOW 증거 1건은 `{ handId, playerId, position, cards, board, lastStreet, spotKeys, outcome, wonGross }`
  입니다. `outcome`은 WON / LOST / **UNKNOWN** — 그 공개가 실제로 겨룬 쇼다운에서 나온 게 아니면
  추측하지 않고 `UNKNOWN`을 씁니다.
- `cards`는 **1장일 수도 있습니다** (부분 공개가 규칙상 가능). 그래서 DB CHECK는 "2장이어야 한다"가
  아니라 텍스트 길이 2 또는 5(1장 또는 2장)를 허용합니다.

## 12. AnalysisRun — 분석 실행 1회의 알고리즘

`세션 분석 및 반영` 버튼 한 번이 하나의 **run**입니다.

1. `{ sessionId }`를 zod로 재검증(서버 액션은 공개 엔드포인트이므로 입력은 언제나 불신).
   존재하지 않는 세션 → `NOT_FOUND`. **닫힌 세션은 허용** — 세션 후 분석이 이 기능의 존재 이유입니다.
2. `startedAt` 기록.
3. 이 세션의 완료 핸드 목록을 읽어 `sessionHandCount`를 얻습니다.
4. 이 세션의 완료 핸드에 연결된 **플레이어 목록**을 얻습니다. 세션은 "누구를 다시 계산할지"를
   **발견하는 범위**일 뿐, 계산 입력이 아닙니다.
   - 한 명도 없으면 → `NO_ELIGIBLE_HANDS`, `runId: null`, **`analysis_runs` 행을 쓰지 않습니다.**
     검증할 입력 자체가 없는 감사 기록은 거짓말이기 때문입니다.
5. 플레이어별로 (쓰기 없이 계획만):
   - 그 플레이어의 **전체 세션에 걸친 완료 핸드 id 목록**을 읽습니다 (§13, §16).
   - `inputIdentityHash(ids)`와 최신 스냅샷의 신원을 비교 → `NO_CHANGES` 게이트.
   - 통과하면 핸드를 로드하고 `computePlayerModel`로 **전부 다시 계산**.
6. `finishedAt` 기록, run id와 snapshot id 발급(모든 id/시각은 주입 — 도메인은 시계를 읽지 않습니다).
7. **`insertAnalysisResults` 단 한 번의 호출**로 run 헤더 + 모든 플레이어 결과 + 모든 새 스냅샷을
   **하나의 트랜잭션**에 씁니다. 전부 아니면 전무(all-or-nothing).
8. 요약 생성. `modelVersion`은 서비스가 고르지 않고 **저장소가 배정한 값을 되읽습니다**.

**실패 처리 (조용한 성공 금지):**

| 상황 | 결과 |
| --- | --- |
| 한 플레이어의 계산 실패 | 그 사람만 `FAILED` + 사유 저장. **나머지는 정상적으로 스냅샷을 받음** |
| 일부 실패 | run `status = PARTIAL` |
| 전원 실패 | run `status = FAILED`, 스냅샷 없음 |
| 아무도 실패 안 함 (전원 `NO_CHANGES` 포함) | `SUCCESS` — 바뀐 게 없는 실행도 성공한 실행입니다 |
| 쓰기 자체가 실패 | 아무것도 저장되지 않고, 저장소의 코드/메시지를 그대로 사용자에게 |

상태는 **선택되는 게 아니라 실패 개수에서 계산**됩니다. 그래서 "전부 성공"이라고 거짓말할 구조적
여지가 없습니다. 그리고 **분석은 원본 히스토리를 절대 쓰지도 지우지도 않습니다** — 유일한 쓰기 경로가
`insertAnalysisResults`이고, 그건 파생 테이블만 건드립니다. 게다가 §4의 트리거가 물리적으로 막습니다.

## 13. Player Model Snapshot 알고리즘과 NO_CHANGES 게이트

### 13.1 전량 재계산 (full recomputation)

스냅샷은 **그 플레이어에게 연결된 모든 완료 핸드**로부터 **처음부터 다시** 계산됩니다.
`이전 값 + 이번 델타` 같은 증분 산술은 **어디에도 없습니다**. 이것이 "두 번 눌러도 두 배가 되지
않는다"의 근본 이유입니다 — 두 번 계산해도 같은 입력이면 같은 답이 나옵니다.

### 13.2 NO_CHANGES 게이트

```
hash   = inputIdentityHash(그 플레이어의 전체 완료 핸드 id 목록)
latest = 그 플레이어의 최신 스냅샷 신원
if latest ≠ null
   and latest.algorithmVersion === ANALYSIS_ALGORITHM_VERSION
   and latest.inputHash === hash
→ NO_CHANGES: 계산도 안 하고, 스냅샷도 안 씀
```

**두 조건을 모두 봅니다** (ADR-0062c). 알고리즘이 바뀌었는데 해시가 같다면 "같은 질문에 대한 다른
답"이고, 알고리즘이 같은데 핸드 집합이 늘었다면 "다른 질문에 대한 같은 답"입니다. 어느 쪽이든 새
스냅샷이 나와야 합니다. 하나만 비교하면 둘 중 한 방향으로 모델이 조용히 얼어붙습니다.

**해시는 반드시 "전체 집합"에 대해 계산해야 합니다.** 만약 이번 세션의 핸드만 넘긴다면, 해시가 매번
달라져서 **클릭할 때마다 새 스냅샷**이 생기고, 게다가 매번 더 적은 히스토리로 계산된 스냅샷이
쌓입니다 — 가능한 최악의 방향입니다. 이 경고는 `analysis-service.ts` 최상단 주석에 못 박혀 있습니다.

`inputIdentityHash`는 FNV-1a 64비트를 정렬된 id 목록에 적용한 값(16자리 소문자 hex)입니다. 정렬 후
해시하므로 **순서와 무관**하고, 개수를 접두어로 붙이고 `\n`으로 구분하므로 이어붙이기 충돌도
막습니다. 암호학적 해시가 아닌 이유는 명시적으로 논증되어 있습니다: 입력이 사용자 본인의 로컬 DB에서
나온 id이고 공격자가 없으며, 충돌의 유일한 결과는 "새 핸드가 왔는데 `NO_CHANGES`로 보고"뿐입니다.

게이트는 **쓰기뿐 아니라 계산 자체를 건너뜁니다** — 1000핸드 재클릭이 608ms가 아니라 4ms입니다 (§17).

### 13.3 결정론

`analysis-core`에는 시계도, 난수도, id 생성도 없습니다. 모든 목록은 명시적 키로 정렬되며,
신뢰도 계산은 순수 정수 산술이라 기계가 달라도 비트 단위로 같습니다. 테스트가
**서로 다른 두 DB에서 만든 스냅샷 내용이 `JSON.stringify` 수준에서 동일**함을 확인합니다.

## 14. 신뢰도(confidence) 공식

```
confidenceWeightBps(n, K) = round(10000 · n / (n + K)),  K = 30
```

- `n`은 **그 상황의 기회 수**입니다. 총 핸드 수가 아닙니다.
- 표시 상태: `n < 5` → **UNKNOWN**, `5 ≤ n < 30` → **LEARNING**, `n ≥ 30` → **KNOWN**.
- 이 숫자들(K = 30, 임계값 5와 30)은 전부 **PRODUCT HEURISTIC**입니다 — 포커의 진리가 아니라 제품
  판단이며, `packages/player-core/src/modelConfig.ts` 한 곳에 모여 있고 그렇게 주석에 명시돼 있습니다.
- 구현은 순수 정수 산술 `floor((2·numerator + denominator) / (2·denominator))` (반올림 half-up)이라
  플랫폼에 상관없이 비트 단위로 동일합니다. 스냅샷을 동등 비교하기 때문에 이게 중요합니다.

손으로 검증된 값들 (전부 테스트에 있음):

| n | 0 | 1 | 5 | 14 | 18 | 22 | 30 | 90 | 270 | 2970 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| bps | 0 | 323 | 1429 | 3182 | 3750 | 4231 | 5000 | 7500 | 9000 | 9900 |

`n = K = 30`에서 정확히 절반(5000)인 것은 공식의 구조상 당연합니다.

**중요:** 이건 ADR-0036의 `ConfidenceLevel`(INSUFFICIENT / LOW / MEDIUM / HIGH)을 **대체하지 않습니다.**
둘은 별개의 타입이고, 서로 암묵적으로 변환되지 않습니다. ADR-0036은 기존 화면에서 그대로 유효합니다.

**정직성 규칙:** `UNKNOWN`은 "낮은 퍼센트"가 아니라 **별개의 상태**로 렌더링됩니다. 화면에는 `—`와
`신뢰도 미확인`이 뜨고, 카운트는 여전히 보여줍니다. 관찰 4번짜리 통계는 "약한 지식"이 아니라
**지식 없음**이기 때문입니다.

**신뢰도는 상황별입니다.** 1000핸드를 관찰했다는 사실은, 7번밖에 나오지 않은 상황에 대해 아무것도
말해주지 않습니다. 그래서 신뢰도는 스냅샷 전체에 한 번, 그리고 **모든 스탯 행과 모든 상황 행에
각각** 붙습니다.

저장 방식도 정직합니다: **가중치(bps)를 저장하지 않고 기회 수 `n`을 저장**하고, 스냅샷 헤더에
`k`와 두 임계값을 저장합니다. 읽을 때 같은 공식으로 정확히 재현되므로 "카운트만 저장한다"는 원칙이
깨지지 않으면서, 오래된 스냅샷도 그 시점의 설정으로 해석 가능합니다.

## 15. 모델 버전 관리

- 스냅샷은 **불변**이며, 새 계산은 **덮어쓰지 않고 버전을 올립니다**: v1, v2, v3, …
- `model_version = max(그 플레이어의 기존 버전) + 1`을 **쓰기 트랜잭션 안에서** 읽습니다.
- 진짜 보증은 `max()` 읽기가 아니라 **`UNIQUE(player_id, model_version)`** 제약입니다. 두 프로세스가
  경쟁해도 진 쪽은 타입 있는 `CONSTRAINT_VIOLATION`을 받고 **아무것도 쓰지 않습니다** — v1이
  조용히 덮어써지는 일은 불가능합니다.
- 각 스냅샷은 `analysisAlgorithmVersion`(현재 1)과 `inputHash`를 함께 기록하므로, 나중에 "이 버전은
  어떤 알고리즘이 어떤 핸드 집합에서 만든 것인가"를 정확히 답할 수 있습니다.
- 파생 테이블은 insert-only이므로, "전부 지우고 원본에서 다시 만들기"는 **런타임 동작이 아니라
  의도적인 마이그레이션 행위**입니다. 이건 의도된 트레이드오프입니다.
- 각 플레이어의 버전은 **서로 독립**입니다 — 한 명이 v2로 가도 다른 사람은 v1에 남습니다.

## 16. 여러 세션에 걸친 누적

`세션 A`에서 버튼을 누르든 `세션 B`에서 누르든, 계산 입력은 언제나 **그 플레이어의 전체 완료 핸드**
입니다. 세션은 "누가 영향을 받는지" 찾는 범위일 뿐입니다 (ADR-0062b).

그래서 다음이 자연스럽게 따라옵니다 (전부 통합 테스트로 확인):

- 세션 A에서 5핸드 → v1 (`sourceHandCount = 5`). 세션 B에서 4핸드를 더 치고 분석 → **v2의
  `sourceHandCount = 9`** — 14도 아니고 10도 아닙니다. v1은 5인 채로 보존됩니다.
- 세션 A(5핸드) + 세션 B(8핸드)를 같은 닉네임으로 쳤다면, B에서 버튼을 눌렀을 때 스냅샷은 **13핸드**
  기준입니다. 그 뒤 A에서 다시 눌러도 → `변경 없음`.
- 이번 세션에 없던 플레이어는 그대로 유지됩니다 — 남의 세션이 내 모델을 흔들지 않습니다.
- 요약의 `총 관찰`은 그 사람의 **전체 히스토리**, `이번 추가`는 직전 스냅샷 대비 증가분,
  세션 자체의 핸드 수는 run 수준의 `sessionHandCount`로 따로 표시됩니다.
- 첫 스냅샷의 `이번 추가`는 `null` → 화면에 **`—`** 로 표시됩니다. 전체 히스토리를 "증가분"으로
  보여주면 일어나지 않은 성장처럼 읽히기 때문입니다.

## 17. 분석 성능 (실측)

측정 조건: Apple M 시리즈, 인메모리 SQLite, 세션당 3명, 모든 플레이어가 모든 핸드에 참여.
(`GTO_SELF_BENCH=1`일 때만 도는 옵트인 벤치이므로 CI에서는 벽시계 단정이 실행되지 않습니다.)

| 핸드 수 | 생성 + 저장 | **`runSessionAnalysis`** | 재실행 (`NO_CHANGES`) |
| --- | --- | --- | --- |
| 100 | 196 ms | **88 ms** | 1.6 ms |
| 500 | 714 ms | **347 ms** | 2.6 ms |
| 1000 | 1331 ms | **608 ms** | 4.1 ms |

해석: **핸드당 실행당 약 0.6ms**, 핸드 수에 선형. 1000핸드 × 3명 = 3000회 추출이 608ms입니다.
전량 재계산이 충분히 빠르므로, **증분 계산이라는 복잡도를 도입하지 않았습니다** — 필요하다는 증거가
없기 때문입니다. 재클릭 경로는 플레이어당 인덱스 조회 2회뿐이라 사실상 공짜이고, 이것이 멱등성
게이트가 정확성 다음으로 사주는 두 번째 이득입니다.

벤치의 유일한 단정은 "핸드당 200ms"라는 일부러 터무니없이 느슨한 상한입니다 — 바쁜 노트북을 잡으려는
게 아니라 **복잡도 회귀**를 잡으려는 장치입니다.

## 18. 왜 전략 추천은 아직 바뀌지 않는가

이건 버그가 아니라 **이번 마일스톤의 수용 조건(acceptance blocker)** 입니다 (prompt §39, ADR-0062g).
플레이어 모델은 지식을 **만들 뿐**, 아직 **쓰지 않습니다**.

세 겹으로 강제됩니다.

1. **패키지 레이어링 (ADR-0061, ESLint 강제).** `strategy-core`와 `gto-core`는 `player-core`,
   `analysis-core`, `@gto-self/db`를 **import 할 수 없습니다.** 독립 리뷰가 12개 방향의 금지된
   import를 실제로 넣어보고 전부 에러가 나는 것을 확인했습니다.
2. **정적 tripwire 테스트 (R1 수정으로 추가).** `packages/strategy-core/tests/layering.test.ts`가
   `strategy-core`와 `gto-core`의 소스를 **텍스트로** 훑어서 모든 모듈 지정자(import, re-export,
   side-effect import, 동적 `import()`, `require()`)와 `package.json` 의존성에 금지 패키지가 없음을
   단정합니다. 텍스트로 읽는 이유는, **타입 전용 import야말로 플레이어 모델 파라미터가 처음 들어오는
   방식**이고 그건 런타임 import 그래프 검사로는 안 보이기 때문입니다. 스캐너 자체를 검증하는
   자가 테스트 2개도 포함되어 있어, 정규식이 망가져서 통과하는 일이 없습니다.
3. **행동 고정 테스트.** 고정된 프리플랍 질의와 플랍 질의를 Strategy Panel이 실제로 쓰는
   `computeStrategy`로 평가해 문자열로 굳혀 두고, 히스토리를 넣고 실제 분석을 돌려 스냅샷이
   만들어진 것을 확인한 뒤(비어 있지 않음을 단정), 다시 평가해 **완전히 같은 문자열**임을 요구합니다.
   추가로 `computeStrategy`의 시그니처 자리에 "이 파라미터 목록은 §39에 대해 load-bearing이며,
   선택적 `playerModel` 옵션을 추가하는 것도 여기에 해당하고, ADR 없이는 바꿀 수 없다"는 주석이
   달려 있습니다.
4. **화면의 말.** 분석 요약에는 언제나 다음 문장이 붙습니다:
   `플레이어 모델이 업데이트되었습니다. 현재 기본전략 추천에는 아직 반영되지 않습니다.`
   두 번째 문장은 **모든 상태에서 무조건** 붙는 상수입니다.

C2가 이 경계를 넘는 날, 위 3번 테스트가 **의식적으로, ADR과 함께** 바뀌어야 하는 지점입니다.

### 19.2 그 밖의 구조적 한계

- **진행 중인 핸드는 리로드 시 사라집니다** (§3, ADR-0059의 의도된 경계).
- **보드 텍스처, 스택 깊이, 3-way/4-way 구분이 상황 키에 없습니다** (§10 — 각각 이유가 있습니다).
- **`observationCount` / `showCount`는 run 수준에서는 "이번에 만든 스냅샷"만 셉니다.** 전원
  `NO_CHANGES`인 실행은 0을 기록합니다. 이건 감사 필드이고, 플레이어별 진실은 스냅샷에 있습니다.
- **벳 사이즈 관찰은 저장되지만 아직 화면에 없습니다.** 데이터는 다 있고, 렌더링만 없습니다.
- **상황 목록은 화면에서 8개로 캡됩니다** (모델은 전부 보관, 제목에 두 숫자를 다 표시).
- **모델 프로필로 가는 입구는 분석 요약의 행뿐입니다** — 펠트의 좌석에서 바로 열 수는 없습니다.
- **`inputIdentityHash`는 암호학적 해시가 아닙니다** (§13.2 — 근거와 함께 문서화된 트레이드오프).
- **트리거 유지보수는 수동입니다.** drizzle-kit은 트리거를 생성하지 않으므로, 새 파생 테이블은
  손으로 쓴 마이그레이션과 26개짜리 트리거 목록 갱신이 함께 필요합니다.

## 20. Strategy C2가 언젠가 소비하게 될 것

C2(적응형 추천)는 **이번 마일스톤의 범위 밖**이고 오늘 import 경로조차 없습니다. 다만 이번에 만든
데이터는 C2가 필요로 할 모양을 이미 갖추고 있습니다.

C2가 읽게 될 것:

- **`player_model_snapshots`의 최신 버전** — 플레이어별 불변 스냅샷.
- **`player_model_stats`** — VPIP/PFR/3Bet/폴드투c-bet 등, 전체 버킷과 포지션 버킷 각각.
- **`player_spot_stats`** — "BB vs BTN 오픈에서 폴드 59%" 같은 상황별 분포. C2가 실제로 필요로 하는
  것은 대개 이쪽입니다.
- **상황별 신뢰도 `n`과 스냅샷의 `k`/임계값** — 이것이 "REFERENCE와 경험값을 **얼마나** 섞을지"의
  가중치가 됩니다. `confidenceWeightBps`가 애초에 연속적인 가중치인 이유가 이것입니다: 작은 표본이
  적은 지식처럼 보여야 해서가 아니라, **미래의 C2가 섞을 무언가가 필요해서** 만든 값입니다.
- **`player_model_bet_sizes`** — 원본 milliBB가 그대로 있으므로 사이징 성향에 쓸 수 있습니다.
- **`player_model_show_evidence`** — 실제로 보여준 카드. 레인지 추정의 유일한 직접 증거입니다.

C2가 넘어야 할 문턱 (지금 일부러 막아 둔 것들):

1. ADR-0061의 레이어링 — `strategy-core`가 `player-core`/`analysis-core`를 못 읽습니다. C2는
   **앱 레이어에서 REFERENCE 결과와 모델을 결합**하거나, 새 ADR로 레이어링을 바꿔야 합니다.
2. `layering.test.ts`와 §39 행동 고정 테스트 — 둘 다 **의식적으로** 바뀌어야 합니다.
3. `computeStrategy`의 파라미터 목록에 달린 경고 주석.
4. UI 표기 — 어떤 추천이 REFERENCE이고 어떤 것이 모델 반영인지 사용자가 반드시 구분할 수 있어야
   합니다. 그리고 모델 수치는 GTO가 아니라 **관찰된 경향**이라는 사실이 절대 흐려지면 안 됩니다
   (CLAUDE.md 규칙 2).

### B~F. 상황별 계산

#### ① BB vs BTN Open (상황 키 `BB_VS_BTN_OPEN`)

   **`진행 중인 핸드가 끝나면 분석할 수 있습니다.`** 라고 이유가 표시되는지 봅니다.
   (이유 없이 비활성인 버튼은 고장 난 앱처럼 읽히므로, 이유는 항상 보입니다.)
5. 카드 팔레트에서 히어로의 두 장을 입력한 뒤 다섯 번 폴드시킵니다. → **`저장된 핸드 1`**, 버튼 다시 활성.
6. 두 번째 핸드를 쇼다운까지 진행합니다: 두 명만 남기고 폴드시킨 뒤 모든 스트리트를 체크로 넘기면서
   팔레트로 **플랍 / 턴 / 리버** 카드를 입력합니다.
7. **정산** 단계에서 한 상대에게 **`오픈`** 을 눌러 그 사람의 카드 두 장을 입력합니다. 다른 사람은
   **`머크`** 로 둡니다. 승자를 고르고 제출합니다. → **`저장된 핸드 2`**
8. 세 번째 핸드는 한 좌석을 **자리비움**으로 두고 칩니다 (그 좌석의 `자리비움` 칩을 누른 뒤 `핸드 시작` —
   그 좌석에 **딜 제외** 표시가 뜹니다). 폴드로 마무리합니다. → **`저장된 핸드 3`**
9. **`세션 분석 및 반영`** 을 누릅니다.
10. 요약을 읽습니다: **Hands 3 / Players 6 / SHOW evidence 1 / 완료**, 그리고 다음 문장이 그대로
    있는지 확인합니다 —
    **`플레이어 모델이 업데이트되었습니다. 현재 기본전략 추천에는 아직 반영되지 않습니다.`**
11. 카드를 공개했던 플레이어 행에서 **`프로필 보기`** 를 누릅니다. **총 관찰 핸드**, **모델 버전 v1**,
    **SHOW 증거 1**을 확인하고, **모든 스탯 행이 퍼센트 옆에 `기회 N`을 함께 표시**하는지 봅니다.
    표본이 작은 항목은 지어낸 퍼센트 대신 **`—`** 와 **`신뢰도 미확인`** 으로 나와야 합니다.
12. 자리비움이었던 플레이어의 **`프로필 보기`** 를 누릅니다. 그 사람의 **총 관찰 핸드는 3이 아니라 2**
    여야 합니다. (자리비움 좌석은 그 핸드에 연결되지 않습니다.)
13. **`Esc`** 로 닫고 **`세션 분석 및 반영`** 을 **다시** 누릅니다. 모든 행이 **`변경 없음`** 이 되고,
    총 관찰은 **두 배가 되지 않으며**, **`이번 추가`는 0**, **모델 버전은 그대로 v1** 이어야 합니다.
    (= 멱등성 확인)
14. **`Esc`** 로 닫고 **`핸드 시작`**, 버튼까지 폴드시킨 뒤 우측 **기본전략 · REFERENCE** 패널을
    읽습니다. 추천, 빈도, 사이징이 **분석을 돌리기 전과 완전히 동일**해야 합니다. (= §39 확인)

**선택 추가 (B1 회귀 확인):** 13~14단계 사이에 **페이지를 새로고침한 뒤 핸드를 하나 더 쳐 보세요.**
저장 실패 배너가 뜨지 않고 `저장된 핸드`가 정상적으로 1 증가해야 합니다. 이것이 R1의 블로커가
수정되었는지 보는 가장 빠른 방법입니다.
